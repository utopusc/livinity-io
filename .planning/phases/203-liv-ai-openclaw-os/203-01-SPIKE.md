## Two-tier reality check (CRITICAL distinction)

The repos involved split cleanly into two halves — easy to confuse on first read:

| Layer | Repo / npm | Role | Where it lives in Phase 203 |
|-------|-----------|------|-----------------------------|
| **Gateway** | `openclaw` npm (`github.com/openclaw/openclaw`) | The Node WebSocket gateway binary that owns LLM dispatch, sessions, channels, agents, plugin loading, HTTP routes. | Installed via `pnpm add openclaw` in `liv-claw-gateway` workspace package. Run via `systemd` as `openclaw gateway run` (Plan 203-03). |
| **Workspace plugin** | `openclaw-os` (`github.com/thesysdev/openclaw-os`) — npm `@openuidev/openclaw-os-plugin@0.1.5` | The plugin that bundles the Next.js claw-client UI + the 9 OpenUI tools + the `before_prompt_build` / `before_tool_call` hooks + the apps/artifacts/notifications/uploads stores. | Cloned to `livos/packages/liv-claw-os/` (Plan 203-02) and rebranded as Liv AI. Loaded by the gateway as a plugin (NOT a separate process). |

The plugin runs **inside the gateway process** — the README's "two services" mental model
(gateway + plugin) refers to the systemd unit topology in D-203-04, but at the process
level the plugin is a registered extension, not a child process. The
`liv-claw-plugin.service` unit in D-203-04 needs revisiting in light of this — see
"Risks / surprises" below.

**Env-var override path** — `~/.openclaw/openclaw.json` `env: { … }` block is the
canonical place; raw process env vars (e.g. `ANTHROPIC_API_KEY` exported in systemd
`Environment=`) are honored too because the gateway reads `process.env` during
provider resolve. For LivOS, the cleanest write-path on Mini PC is the systemd unit's
`Environment=ANTHROPIC_API_KEY=...` directive (Plan 203-03 territory) — no config-file
mutation required, no Redis bridging needed for v1.

**Provider auth resolution** — `openclaw onboard` interactively writes the auth into
config; non-interactively use `openclaw onboard --anthropic-api-key "$KEY"` or set the
env var and let provider plugins discover it. Verified at runtime: even with a clearly
invalid `ANTHROPIC_API_KEY=sk-ant-test-001`, the gateway booted clean — provider auth is
lazy (validated on first request, not at boot). This means we can ship the systemd unit
without operator pre-onboarding; first-request UX will surface the auth gate.

## Tool registration API (plugin hook signature + example)

Plugins register tools via `api.registerTool(factory, opts)`. Tools are NOT JSON
manifests — they are TypeScript factories returning a tool descriptor with embedded
`execute` closure. Hot-reload is **NOT supported** (restart required, matches
INV-203-08-implied behaviour and D-203-04 service restart model).

**Verbatim type contract** (from
`node_modules/openclaw/dist/plugin-sdk/src/plugins/types.d.ts:2065`):
```ts
registerTool: (
  tool: AnyAgentTool | OpenClawPluginToolFactory,
  opts?: OpenClawPluginToolOptions
) => void;
```

**Real example** (`packages/claw-plugin/src/index.ts:538`, the `create_markdown_artifact`
tool):
```ts
api.registerTool(
  (ctx: OpenClawPluginToolContext) => ({
    name: "create_markdown_artifact",
    label: "Create Markdown Artifact",
    description: "Create a durable markdown document artifact …",
    parameters: {
      type: "object" as const,
      properties: {
        title:   { type: "string", description: "Short, descriptive title" },
        content: { type: "string", description: "Full markdown content" },
      },
      required: ["title", "content"],
    },
    execute: async (_id, params) => {
      const artifact = await getStore().create({
        kind: "markdown",
        title: params.title,
        content: params.content,
        source: { agentId: ctx.agentId, sessionKey: ctx.sessionKey },
      });
      return jsonResult({ id: artifact.id, title: artifact.title });
    },
  }),
  { name: "create_markdown_artifact" }
);
```

**Plan 203-06 implication**: the 9 Luse `luse_*` tools + 11 LivOS built-ins (weather,
get_current_time, ui_render, the 8 existing P200-C tools) will each be a one-line
`api.registerTool(factory, { name })` call. The factory's `execute` closure is the
escape hatch — it does an `await fetch('http://127.0.0.1:8080/internal/tools/{name}', …)`
to livinityd's existing tool dispatcher (which retains the ApprovalManager HITL gate per
D-203-14). 20 tools × ~25 lines each = the entire `liv-claw-plugin/src/tools/` directory
is ~500 LOC of glue.

The upstream claw-plugin registers exactly 9 tools (`create_markdown_artifact`,
`update_markdown_artifact`, `get_artifact`, `list_artifacts`, `db_query`, `db_execute`,
`app_create`, `get_app`, `app_update` — matching `openclaw.plugin.json` `contracts.tools`).
After Plan 203-06 rebrand, the registered set becomes:

- **Inherited from upstream** (rebranded but kept): `create_markdown_artifact`,
  `update_markdown_artifact`, `get_artifact`, `list_artifacts`, `db_query`, `db_execute`,
  `app_create`, `get_app`, `app_update` (D-203-09 wires `app_*` to livinityd Postgres)
- **Added from LivOS**: 9 `luse_*` + 11 LivOS built-ins = 20 new entries
- **Total**: 29 tools surfaced to the gateway

## HTTP / WebSocket surface (ports, endpoints, auth shape)

**Ports** (verified at boot):

| Port | Listener | Auth | Purpose |
|------|----------|------|---------|
| 18789 | gateway (default; we used 18790 in spike) | `gateway.auth.token` | WebSocket gateway control plane + HTTP plugin routes |
| 18792 | browser/server (auto-spawned) | per-listener generated token | Browser control plane for the `browser` plugin |

**HTTP endpoints verified live** on port 18790:

| Path | Method | Auth | Response |
|------|--------|------|----------|
| `/health` | GET | none | `{"ok":true,"status":"live"}` |
| `/` | GET | none | 200 (gateway home / health) |
| `/plugins/openclawos` | GET | `plugin` (token in URL fragment) | 404 in spike (plugin not installed); 200 + claw-client `index.html` when plugin is installed |

**Plugin HTTP routes** are registered via `api.registerHttpRoute({ path, auth: "plugin", … })`.
The `auth: "plugin"` mode resolves a per-plugin token tied to the gateway's main token.
**Browser tabs load the UI from the gateway origin** (`http://<gateway>:18789/plugins/openclawos`)
which means **no CORS dance, no allowed-origins config, no separate Next.js process**.
This is the design's standout feature: gateway-served same-origin UI.

**WebSocket handshake** — the claw-client connects back over `ws://<gateway>:18789/`
(same origin) carrying `connect.params.auth.token` (when `--auth token`) or nothing
(when `--auth none`). The gateway-protocol type bundle the claw-client uses is inlined
from upstream openclaw at
`packages/claw-client/src/lib/gateway/types.ts` (per AGENTS.md guidance — `openclaw`
package only exports `plugin-sdk/*` subpaths publicly, not protocol types).

**Plan 203-05 bridge** (LIVINITY_SESSION JWT → openclaw device token): livinityd issues a
short-lived openclaw device token (5 min TTL per D-203-12 / T-203-02) after verifying the
LIVINITY_SESSION cookie. The parent UI loads
`/liv-ai-app/` (Caddy-proxied to `:18789`) → the claw-client opens its WebSocket back to
the same origin with the issued token in the fragment + connect.params. Browser tab,
plugin HTTP route, WebSocket, agent dispatch — all same-origin, all on port 18789.

## claw-client serving (gateway-native vs plugin-bundled)

**Plugin-bundled (NOT gateway-native).** The Next.js workspace UI lives in
`packages/claw-client/`, builds via `next.config.ts` with `output: "export"`, lands a
static export in `packages/claw-client/out/`, then the plugin's `bundle-ui` script
(`packages/claw-plugin/package.json:scripts.bundle-ui`) copies it to
`packages/claw-plugin/static/`. The plugin's `register(api)` callback registers an HTTP
route at `/plugins/openclawos` whose handler streams files out of that `static/` dir
with MIME inference + path-traversal guard
(`packages/claw-plugin/src/index.ts:198-242`).

Concretely:
```bash
# In packages/claw-plugin:
pnpm bundle-ui   # → cd ../claw-client && pnpm build → shx cp -r out ../claw-plugin/static
pnpm build       # → esbuild src/index.ts → dist/index.js (single bundled file)
pnpm prepack     # → bundle-ui + build (what `npm publish` runs)
```

- The `liv-claw-os/` clone build pipeline must produce both
  `packages/liv-claw-plugin/static/` (Next.js static export) AND
  `packages/liv-claw-plugin/dist/index.js` (esbuild bundle) before the plugin is loadable.

## Memory / threads (built-in surface vs external integration)

**Built-in.** The gateway has its own session/thread/message model — see AGENTS.md
mental model. Sessions are keyed `agent:<agentId>:<channel>:<senderId?>` and message
history is stored under that key in the gateway's own SQLite/JSON state. The claw-client
appends `:openclaw-os` to the session key to mark its sessions for the plugin's
`before_prompt_build` hook.

**Plan 203-07 interplay with `livos_agents` table** (INV-202-02): Phase 202's
`livos_agents` Postgres table holds the LivOS-side agent metadata (id, name, instructions,
model, tools[], parentAgentId, scheduleCron, …). The new LivOSAgent thin wrapper
(D-203-06 / D-203-07) projects each `livos_agents` row into a gateway-side agent config
at boot — i.e. when `LivOSAgent.start()` runs, it calls the gateway's
`agents.upsert(...)` RPC (or equivalent — see Plan 203-07 spike note below) for every
row in `livos_agents`. The gateway then owns the session store + message history per
agent. Phase 202's table remains the source of truth for "what agents exist", the
gateway owns "what each agent has said".

**Memory bridge clarification**: D-203-06 mentions a "Memory bridge" component of
LivOSAgent — at this layer it's a thin two-way sync between `livos_agents` (Postgres)
and the gateway's agent registry (in-process + persisted under `tasks/`), NOT a
custom memory provider plugin. The 57-provider catalog includes `memory-lancedb` and
the bundled `memory-core` plugin — those are agent-memory providers, separate concern.

## HITL / approval hooks (built-in vs plugin-level)

**Plugin-level via `before_tool_call` hook.** No built-in HITL gate. The hook signature
is verified in `node_modules/openclaw/dist/plugin-sdk/src/plugins/hook-types.d.ts:657`:

```ts
before_tool_call: (event: PluginHookBeforeToolCallEvent, ctx: PluginHookToolContext)
  => Promise<PluginHookBeforeToolCallResult | void> | …;
```

Subscribed via `api.on("before_tool_call", handler)`. The handler runs BEFORE the tool
executes; returning a result with rejection/block payload prevents the call (the
upstream claw-plugin uses this to gate `app_create` / `app_update` until the agent has
`read` the SKILL.md — see
`packages/claw-plugin/src/index.ts:350-380`).

**Plan 203-06 HITL wiring** (D-203-14): the rebranded `liv-claw-plugin` registers ONE
`before_tool_call` hook that:
1. Looks up the tool name in a hardcoded `DESTRUCTIVE_TOOLS` set
   (luse_screenshot, luse_click, luse_type, luse_write_file, db_execute, app_create, …)
2. If destructive, makes a sync HTTP RPC to livinityd's `POST /internal/approvals/check`
   carrying `{toolName, params, sessionKey, agentId}` — livinityd's existing
   ApprovalManager (from Phase 195) consults Redis state, possibly emits a Server-Sent
   Event to the operator UI, blocks until approve/deny
3. If approved, returns void (call proceeds); if denied, returns a result payload
   indicating refusal

INV-203-04 (HITL gate fires for every destructive tool call) is preserved by this
single hook handler.

All other hooks (`before_prompt_build`, `agent_turn_prepare`,
`heartbeat_prompt_contribution`, etc.) we leave to upstream defaults.

The full 37-hook surface (verbatim from
`node_modules/openclaw/dist/plugin-sdk/src/plugins/hook-types.d.ts:21`):


## Branch A confirmation (YES — confirmed)

> **VERDICT: BRANCH A LOCK PRESERVED. NO ESCALATION REQUIRED.**

Three independent pieces of evidence confirm openclaw self-dispatches LLM:

1. **Boot-time log line**: `2026-05-23T10:49:17 [gateway] agent model: openai/gpt-5.5
   (thinking=medium, fast=off)` — the gateway resolved a model on its own, before any
   plugin loaded, and held it as the default for the seed "dev" agent. A backend-callback
   architecture would not resolve a model at boot.
2. **57-provider docs catalog under `node_modules/openclaw/docs/providers/`** with full
   API-key onboarding flow (`openclaw onboard --anthropic-api-key …`) and
   `agents.defaults.model.primary` config key — these are first-class gateway concerns,
   not plugin extension points.
3. **Type surface**: the `OpenClawPluginApi` interface exposes provider-plugin
   registration hooks (`registerChannel`, `registerMemoryEmbeddingProvider`,
   `registerCliBackend`, etc.) BUT calling them is OPTIONAL — provider resolution happens
   in the gateway's `provider-runtime` (~30 plugin-sdk types prefixed `Provider*`), and
   the 57 built-in providers (including all major commercial LLM APIs) are bundled.
   No "where do I send LLM requests" callback exists for the operator to wire.

Branch B (delegated dispatch) would require the gateway to expose an
`api.registerLlmDispatcher(handler)` or equivalent, where every LLM call gets POST'd to
an operator backend. **That API does NOT exist.** The reverse direction (operator
plugins implementing custom providers via `provider-entry`) IS supported, but for our
use case (proxy Anthropic/OpenAI via API key) it's unnecessary — openclaw already ships
those providers.

D-203-06 lock holds. Plan 203-07 implements the LivOSAgent thin-wrapper path as planned.

## Risks / surprises found during spike

1. **D-203-04 service topology needs revision.** CONTEXT says "TWO new systemd units:
   `liv-claw-gateway.service` + `liv-claw-plugin.service` (long-running worker process
   registered with the gateway)." Reality: the openclaw-os plugin runs **inside the
   gateway process** as a `definePluginEntry`-returned extension loaded via jiti
   (or esbuild bundle since 2026.5.x — `dist/index.js`). There is no separate
   long-running worker process for the plugin. Plan 203-03 should ship ONE systemd
   unit (`liv-claw-gateway.service`) that runs `openclaw gateway run` with the plugin
   already installed via `openclaw plugins install`. **Operator should confirm D-203-04
   adjustment** — file as a minor CONTEXT amendment after 203-01 closes.

2. **`openclaw plugins install ./packages/liv-claw-plugin --force` requires the
   `plugins.allow` list to include `openclaw-os-plugin`** (or the list to be empty for
   allow-all). Plan 203-03 systemd unit needs a `preStart` that runs
   `openclaw config set plugins.allow '["openclaw-os-plugin", …]'` OR ships an
   `openclaw.json` template with the right allow-list seeded.

3. **`pnpm prepack` runs `bundle-ui` which runs `cd ../claw-client && pnpm install
   --frozen-lockfile=false && pnpm build`.** This means installing the plugin into the
   gateway requires the claw-client's Next.js build to succeed first. Plan 203-12
   (Mini PC deploy) needs `update.sh` to handle BOTH builds — gateway prepack + plugin
   prepack. The existing `update.sh` flow handles UI builds for livinityd's
   liv-ai-app subapp; we'd add a parallel stage for liv-claw-* builds.

4. **Auth UX gotcha**: `--auth none` worked in spike, but production needs
   `--auth token`. The token gets written to `gateway.auth.token` in
   `~/.openclaw/openclaw.json` and the operator gets the
   `/plugins/openclawos/setup#gateway=ws://…&token=…` URL via `openclaw os url` CLI.
   For LivOS the parent iframe needs to inject this token via the Plan 203-05
   handshake bridge — operator should NEVER see the openclaw URL or token directly.

5. **Lazy provider auth validation** is a feature, not a bug: gateway boots fine with
   `ANTHROPIC_API_KEY=sk-ant-test-001` (invalid). First chat request will fail with a
   provider auth error. Plan 203-13 UAT step 3 (operator types "Show me the weather in
   Istanbul") will be the first request — if the systemd unit's env vars are stale, the
   failure surfaces there. Add a `journalctl | grep "provider auth"` line to UAT.

6. **`openclaw onboard` is interactive by default** — Plan 203-03 should NEVER run
   onboard at boot; all config writing must use `openclaw config set <key> <value>`
   non-interactively (or template the `openclaw.json` directly in update.sh).

7. **Browser plugin auto-spawns on port 18792.** The gateway's bundled `browser` plugin
   starts its own HTTP listener on a derived port. For LivOS on Mini PC this is fine
   (we bind loopback only), but worth noting for any future port-collision audit. If we
   ever need to disable it: `openclaw config set plugins.browser.enabled false`.

8. **Boot time on Windows: ~5.2s.** Mini PC (Linux, faster I/O) should be sub-3s. Plan
   203-12 `systemctl restart liv-claw-gateway` should converge cleanly within 10s.

9. **NO MCP wiring exposed by gateway as plugin extension** for v203's needs. The Luse
   MCP server (Phase 201, livinityd-spawned) stays as-is per D-203-13; tools become
   gateway-registered via `liv-claw-plugin`'s `api.registerTool` calls that proxy back
   to livinityd's MCP bridge over HTTP. No openclaw MCP plugin is used in v203 — this
   matches D-203-13 already.

10. **`docs/openclaw-os-bundling.md` referenced in plugin README does NOT exist** in
    the clone (root README links there, root has no `docs/` dir). Minor — not a blocker,
    but means the upstream "end-user setup story" doc is missing. Plan 203-02 should
    not depend on its content.
