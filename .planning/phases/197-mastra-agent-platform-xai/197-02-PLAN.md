<objective>
Build the `McpBridge` — a Mastra `MCPClient` adapter that consumes computer-use tools from two sources (Luse stdio + selfclaude HTTP) and exposes them to the Liv AI agent (Plan 197-04) as a unified, namespaced tool map. Both sources are independently optional; the bridge gracefully degrades if either is unavailable and never crashes livinityd boot. Destructive tools carry a `requireApproval` metadata flag so the Plan 197-05 SSE layer can pause execution for HITL approval.

Purpose: Liv AI's defining capability is "type a message, see your screen change." That requires computer-use tools. The MCP bridge is the abstraction that lets us swap or compose backends (today Luse + selfclaude; tomorrow Bytebot, OpenAdapt, or anything speaking MCP) without touching the agent definition.

Output: Single new module `livos/packages/livinityd/source/modules/mastra/mcp-bridge.ts` (+ errors + tests). NO modifications to livinityd boot in this plan — Plan 197-04's agent factory consumes the bridge.
</objective>

<!-- Mastra MCPClient contract (https://mastra.ai/docs/mcp/overview) -->
From @mastra/mcp:
```ts
import {MCPClient} from '@mastra/mcp'

const client = new MCPClient({
  id: 'unique-per-client-id',          // MANDATORY — memory leak guard
  servers: {
    luse: {
      command: '/usr/local/bin/luse-mcp',   // stdio
      args: [],
    },
    selfclaude: {
      url: new URL('http://localhost:8090/mcp'),   // HTTP
    },
  },
})

// Returns Mastra tool map: { luse_computer_screenshot: {...}, selfclaude_list_skills: {...} }
const tools = await client.getTools()
```

Note: When MCPClient is given multiple servers in the `servers` map, Mastra automatically namespaces returned tools as `<serverKey>_<toolName>`. Plan 197-02 leverages this by naming server keys `luse` and `selfclaude` so the resulting tool ids are `luse_*` and `selfclaude_*` with no manual prefix logic.
