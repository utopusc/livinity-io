<objective>
Wire the Phase 248-01 backend DisplayManager into Luse's MCP surface so AI agents can call `computer_create_display`, `computer_list_displays`, `computer_kill_display`, and `computer_launch_app_in_display` over the standard MCP JSON-RPC channel. Extend `computer_application` with an optional `display` param so the agent can target an existing display directly.

Purpose: After 248-01 the backend is callable from TypeScript, but agents speak MCP. This plan exposes the same five-method contract through MCP tools and routes calls back into `options.displayManager`. The owner-scope check stays at the manager layer (248-01) — MCP handlers just pass `options.userId` as the calling session and surface the manager's `{ok:false, error:'not-owner'}` response as `isError:true` with a helpful text block.

Output:
- 4 new tool schemas added to LUSE_TOOLS in `luse-tools.ts`
- Optional `display` prop added to `_applicationTool.input_schema.properties`
- 4 new handlers in `buildHandlers()` in `mcp/tools.ts`
- `displayManager` field added to `LuseToolsOptions`
- `computer_application` handler extended to honor explicit `args.display`
- `mcp/server.ts` `main()` constructs `displayManager` from existing redis client and threads it into `registerLuseTools`
- 8+ new vitest cases in `mcp/tools.test.ts`
</objective>
