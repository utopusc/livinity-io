<objective>
Deliver D-131-E tier (a) — page reload survives pinning. After this plan ships, the user can pin N windows, refresh the browser, and the same chips reappear in the TopBar shelf with their windows hydrated (at their previous position / size / route, but in `isPinnedToTopBar: true` collapsed state). Tier (b) — tab close + browser close survival — is Plan 131-03 scope.

This plan delivers ONLY the persistence layer + UI hydration. The underlying app session (a Files watcher, an AI-Chat WebSocket connection, a WebApp Chrome handle) is NOT yet kept alive in the background — the window is re-rendered from scratch on refresh. Tier (b) addresses live-session continuity.

Output:
- Postgres `pinned_windows` table + migration.
- `pinnedWindows.list / .upsert / .delete` tRPC procedures on livinityd.
- `WindowManagerProvider` hydrates pinned windows on mount and mirrors mutations to the backend.
- A UAT log proving refresh-survive works for at least two pinned windows of different app types.
</objective>

Add to `livos/packages/livinityd/source/modules/database/schema.sql`:

```sql
-- Phase 131-02: Pinned-windows registry. Each row = one window the user
-- has pinned to their TopBar shelf. Survives page refresh. Tier-(a)
-- persistence per D-131-E.
CREATE TABLE IF NOT EXISTS pinned_windows (
  user_id      UUID         NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  window_id    TEXT         NOT NULL,
  app_id       TEXT         NOT NULL,
  route        TEXT         NOT NULL,
  title        TEXT         NOT NULL,
  icon         TEXT         NOT NULL,
  position_x   INTEGER      NOT NULL,
  position_y   INTEGER      NOT NULL,
  size_w       INTEGER      NOT NULL,
  size_h       INTEGER      NOT NULL,
  payload_json JSONB,
  pinned_at    TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
  last_seen_at TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
  PRIMARY KEY (user_id, window_id)
);

CREATE INDEX IF NOT EXISTS pinned_windows_user_idx ON pinned_windows (user_id, pinned_at DESC);
```

If the project uses a migration tool (check `livinityd/source/modules/database/migrations/`), add a numbered migration file instead of editing schema.sql directly. Confirm by looking at how the most recent table (v7 multi-user) was added.

`payload_json` is reserved for the Plan 131-03 session contract (frozen state per app type) — it stays NULL in 131-02.

<task id="02-03" type="execute">
<action>
Wire the UI side to hydrate pinned windows on mount and mirror pin/unpin mutations to the backend.

In `livos/packages/ui/src/providers/window-manager.tsx`:

1. On `WindowManagerProvider` mount, call `trpcReact.pinnedWindows.list.useQuery()` (or `useUtils().pinnedWindows.list.fetch()` if you need imperative). For each returned row, dispatch:
   - `OPEN_WINDOW` with the row's appId / route / title / icon / position / size / id.
   - `PIN_TO_TOPBAR` with the same id (so the window mounts in collapsed state, NOT as a fullscreen window).

2. In the `pinWindowToTopBar` callback, after `dispatch({type: 'PIN_TO_TOPBAR', ...})`, also call:
   ```ts
   trpc.pinnedWindows.upsert.mutate({
     windowId, appId, route, title, icon, position, size
   })
   ```
   Look up the current WindowState by id to grab the fields.

3. In the `unpinWindowFromTopBar` callback, after `dispatch(...)`, call:
   ```ts
   trpc.pinnedWindows.delete.mutate({windowId})
   ```

Edge case: if `pinWindowToTopBar` is called for a window the backend doesn't know about (just-opened, never persisted), the upsert handles it (it's an upsert, not an update). No extra wiring needed.

Edge case: if the user is in legacy single-user mode (no user_id), the `authenticatedProcedure` middleware should still resolve to the admin user via `getAdminUser()` per project memory.
</action>
