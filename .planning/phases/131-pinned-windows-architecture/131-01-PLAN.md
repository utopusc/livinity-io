<hypotheses>
The pipeline has six possible failure points. Investigate in order:

**H1 — Stale rect during expand animation:**
The `mousemove` hit-test reads `dropZoneRef.current.getBoundingClientRect()`. The bar expands from 580 → 1180 over 1400ms after drag-start. If the user releases the mouse during the expand animation, the rect read may be stale (sampled before the expand completes). Fix: invalidate the rect cache on every mousemove (already what the code does — but verify the bounding rect actually reflects the in-flight transform).

**H2 — Native vs React MouseEvent mismatch on mouseup:**
`handleMouseUp` is attached via `document.addEventListener('mouseup', handleMouseUp)`. The native event passes a `MouseEvent`, but the function signature is `(e?: MouseEvent) => void` and references `e.clientX`. If the native event isn't actually being forwarded (some wrapper strips it), `emitWindowDragDrop` fires with NaN coordinates and the bbox check returns false. **Most likely root cause.** Verify with a `console.log(e?.clientX, e?.clientY)` at the top of `handleMouseUp`.

**H3 — Effect cleanup ordering:**
The TopBar `useEffect` for `mousemove` depends on `dragState.isDragging`. When the drag ends, `isDragging` flips to false BEFORE the mouseup handler in window.tsx finishes broadcasting the drop event. The cleanup function removes the mousemove listener, which is fine — but the `onWindowDragDrop` subscriber needs to fire AFTER the drop event is emitted. Verify the call order: `setWindowDragState({isDragging: false})` should be called AFTER `emitWindowDragDrop(...)` (currently is, line 110 of window.tsx — confirm).

**H4 — Drop-zone visibility race:**
TopBar's drop-zone div only renders when `isExpanded === true`. `isExpanded = dragState.isDragging || isHoverExpanded`. When `isDragging` flips to false at mouseup, React re-renders and the drop-zone unmounts BEFORE the `onWindowDragDrop` subscriber fires its callback that reads `dropZoneRef.current`. So `dropZoneRef.current` is null when the subscriber runs. **Second most likely root cause.** Fix: read the bbox in the mouseup BEFORE setting `isDragging: false`, OR keep the drop-zone mounted for one extra frame post-drag, OR read the bbox in the window.tsx mouseup and pass it through the event.

**H5 — Sacred SHA pre-commit hook side-effect:**
The repo has a sacred-SHA pre-commit hook. Phase 130-09 may have changed something unrelated and the hook is silently rejecting the commit, but the file's compiled .js is stale. Verify with `git log -p livos/packages/ui/src/providers/window-drag-state.ts` — confirm the file was actually committed and isn't pending.

**H6 — Vite HMR module-instance split:**
`providers/window-drag-state.ts` exports module-level mutable `currentState` + `listeners[]`. Vite HMR can in rare cases create two copies of the module — window.tsx writes to instance A, top-bar.tsx reads from instance B. Symptom: hover preview works (no drag involved) but actual drag-drop is silent. Fix: move the store into a Zustand vanilla store or a React context that's guaranteed to be a single instance.
</hypotheses>

In top-bar.tsx, call `setShelfBBox(dropZoneRef.current.getBoundingClientRect())` whenever the drop-zone mounts / on every mousemove.
