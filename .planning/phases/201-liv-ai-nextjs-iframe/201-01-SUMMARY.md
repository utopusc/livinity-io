## Deviations from Plan

### 1. [Rule 1 — Bug] `--yes` flag rejected by current assistant-ui CLI

- **Found during:** Task 1 (initial scaffold attempt)
- **Issue:** Plan Task 1 prescribed `npx assistant-ui@latest create liv-ai-app -t default --yes`. The current published CLI (assistant-ui v0.x as of 2026-05-23) does not implement `--yes` — `error: unknown option '--yes'`. The CLI is non-interactive by default when project name + `-t` are provided, so the flag is functionally redundant.
- **Fix:** Dropped `--yes`, added `--use-pnpm` (to match workspace toolchain) and `--skip-install` (to defer install to workspace-level `pnpm install`, which is what actually wires the new package into the lockfile).
- **Effective command:** `npx --yes assistant-ui@latest create liv-ai-app -t default --use-pnpm --skip-install`
- **Files modified:** None — fix was a CLI-flag adjustment.
- **Commit:** Folded into the single Plan 201-01 atomic commit.

### 2. [Rule 3 — Blocking Issue] Workspace `pnpm install` fails at `packages/ui` postinstall (Windows POSIX `cp -r` breakage — pre-existing)

- **Found during:** Task 3 (`cd livos && pnpm install`)
- **Issue:** `packages/ui` has a `postinstall` script `npm run copy-tabler-icons` which runs `mkdir -p public/generated-tabler-icons && cp -r ./node_modules/@tabler/icons/icons/. ./public/generated-tabler-icons` — these POSIX commands fail on Windows cmd.exe with `The syntax of the command is incorrect.` Same precedent as Phase 198-02 (documented).
- **Fix:** Retried with `pnpm install --ignore-scripts` (Plan Task 1 explicitly allows this fallback for ELIFECYCLE precedent). Install completed (`Done in 14s using pnpm v10.25.0`). This is a pre-existing repo Windows quirk, NOT caused by Plan 201-01.
- **Files modified:** None.
- **Out-of-scope follow-up:** The `packages/ui` postinstall portability issue is a separate concern (would belong in its own plan) — logged here for awareness but not auto-fixed per executor scope boundary.

### 3. [Rule 3 — Blocking Issue] assistant-ui CLI layout drift: components flat-emitted but `app/assistant.tsx` imports from `@/components/assistant-ui/`

- **Found during:** Task 3 (first `pnpm build` attempt)
- **Issue:** The CLI's shadcn registry emits `thread.tsx` and `threadlist-sidebar.tsx` at `components/thread.tsx` and `components/threadlist-sidebar.tsx` (flat), but the scaffold's own `app/assistant.tsx` imports them as `@/components/assistant-ui/thread` and `@/components/assistant-ui/threadlist-sidebar`. Build failed with `Module not found` × 2. This is an upstream assistant-ui CLI bug — the default template `assistant.tsx` is stale relative to current registry emit paths.
- **Fix:** Moved `components/thread.tsx` → `components/assistant-ui/thread.tsx` and `components/threadlist-sidebar.tsx` → `components/assistant-ui/threadlist-sidebar.tsx`. The two relocated files import their siblings (markdown-text, attachment, tooltip-icon-button, thread-list, github, tool-fallback) via flat `@/components/<x>` paths that resolve correctly (siblings left flat — no further changes needed).
- **Side benefit:** This relocation EXACTLY matches Plan AC#3 wording (`components/assistant-ui/thread.tsx`), so the fix is both a build-unblock and an AC compliance.
- **Files modified:** `mv` of 2 files (both untracked at the time, no `git mv` needed).
- **Commit:** Folded into the single Plan 201-01 atomic commit (both files committed at the post-relocation path).
