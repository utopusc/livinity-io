<objective>
Implement the instance rules and the SC3 icon-recall:
- **SC8 (Native = single instance):** `NATIVE_<id>` is already a singleton appId
  (use-launch-native-app.ts:91) but the hook ALWAYS calls `openWindow`, so a second click spawns a
  duplicate window over the same idempotent stream and closing one kills the shared stream. Add a
  focus-existing guard: if a window with `appId === NATIVE_<id>` exists → recall it (unpin if docked,
  restore if minimized, else focus) instead of opening a new one. This guard ALSO satisfies SC3's
  recall-from-app-icon.
- **SC7 (WebApp = unlimited instances):** `WEBAPP_<id>` is built once per webappId
  (use-launch-webapp.ts:30) so instances fight over one server stream. Make the appId per-instance
  unique (`WEBAPP_<id>_<uuid>`) and update the webappId slicing (windows-container.tsx:33-34,
  window-content.tsx:166-180) to recover the real webappId.

CRITICAL RISK (RESEARCH Open Q2 / Assumption A2): the webapp streaming BACKEND may key spawn/close
by webappId only — two instances would collide. The executor MUST READ the webapp backend FIRST and
confirm concurrency before locking the SC7 change. This is the single biggest schedule risk in the
phase; it is an explicit gated investigation task below.

Purpose: native focus-existing (+ icon-recall), webapp multi-instance.
Output: guarded native launch, unique webapp appId + slicing, backend-concurrency confirmation, tests.
</objective>
