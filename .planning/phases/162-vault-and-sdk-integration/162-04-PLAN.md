<objective>
Refactor `AgentSessionManager.sessions` from a `Map<userId, ActiveSession>` to a Map keyed on the composite `${userId}:${surfaceKind}:${surfaceId}:${connectionId}` shape, so that the same user can run multiple concurrent sessions across different surfaces (Main Chat + WebApp Chat + NativeApp Chat + Autonomous) without one canceling the other.

Today's collision pattern (post Phase 161):
- User opens Main Chat → sessionKey = `admin:54c6caa5` (userId:connectionId)
- User opens WebApp Chat in another tab → sessionKey = `admin:abc01234`
- Both run independently per tab (Phase 161 already added per-connection isolation via `connectionId`)

Today's gap (the v34 motivator):
- An autonomous scheduler (Phase 164) needs to spawn a session as `admin` WITHOUT a tab → no connectionId distinct from the user's existing Main Chat. The autonomous turn would call `cleanup(userId)` and kill the user's Main Chat.
- Same problem for parallel webapp instances: one webapp session would cancel another.

Solution per master plan D-V34-?: structure the key around the SURFACE (where the session originated) not just the connection. `surfaceKind` is one of `'main' | 'webapp' | 'native' | 'autonomous'`. `surfaceId` is the per-surface unique identifier (e.g. a webapp UUID for `webapp`, the nativeAppId for `native`, a scheduler job ID for `autonomous`). `connectionId` stays as the per-WS-connection randomness.

Backward-compat contract (D-V34-?): when `vaultModeConfig === undefined`, the sessionKey shape falls back to the legacy `${userId}:${connectionId}` form so Phase 161's tests continue to pass byte-identical.

Output: 1 modified core source file (sessions Map type + every read/write site), 1 new test file, 1 modified livinityd source file (sessionKey construction at the WS message handler).
</objective>

```typescript
// Phase 162-04 — Surface-aware composite sessionKey.
// Reads surfaceKind + surfaceId from WS URL params (set by the UI hook at
// `?surface=main|webapp|native|autonomous&surfaceId=<id>`) or the WS start
// envelope `raw.surface` field. Defaults to 'main' / 'default' for legacy
// chat that doesn't emit a surface hint.
//
// Backward-compat (D-V34-?): when chat_backend === 'legacy', the sessionKey
// drops surfaceKind + surfaceId so AgentSessionManager keys exactly like
// Phase 161 (and pre-161). Vault mode adds the composite shape.
//
// The composite key shape lets the same userId run parallel sessions for
// Main Chat (`admin:54c6caa5:main:default:conn01`) + WebApp Chat
// (`admin:54c6caa5:webapp:suna-uuid:conn02`) + Autonomous
// (`admin:54c6caa5:autonomous:nightly-backup:conn03`) without one
// canceling the other.

const surfaceKindFromUrl = url.searchParams.get('surface') ?? undefined
const surfaceIdFromUrl = url.searchParams.get('surfaceId') ?? undefined

// In legacy mode, sessionKey shape matches Phase 161 exactly.
// In vault mode, it carries the surface composite tag.
// Note: the surface hint may also arrive in the WS `start` message body
// (raw.surface, raw.surfaceId). We resolve URL first, then defer to body
// in the message handler if URL params were absent.
const buildSessionKey = (surfaceKind?: string, surfaceId?: string): string => {
  if (vaultModeConfig === undefined) {
    // Legacy — Phase 161 byte-identical
    return `${userId}:${connectionId}`
  }
  const sk = surfaceKind ?? 'main'
  const sid = surfaceId ?? 'default'
  return `${userId}:${sk}:${sid}:${connectionId}`
}

let sessionKey = buildSessionKey(surfaceKindFromUrl, surfaceIdFromUrl)
```

Then in the WS message handler, when `raw.type === 'start'`, if `raw.surface` is provided AND we don't already have URL-derived surface info, RECOMPUTE sessionKey:
```typescript
if (raw.type === 'start' && (raw as any).surface && !surfaceKindFromUrl) {
  sessionKey = buildSessionKey((raw as any).surface, (raw as any).surfaceId)
}
```
