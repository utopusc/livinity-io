<objective>
Close Gap 2 (CR-01): `getVncUrl` compares `ctx.currentUser.id` (a PostgreSQL UUID on the
multi-user Mini PC) against `owner_session` (written by the MCP stdio server as the
LUSE_USER_ID string, default 'bruce'). These never match, so EVERY MCP-created display
(:11/:12) returns FORBIDDEN to the UI — the headline VNC feature is non-functional for the
primary use case.

Apply CR-01 Option A: allow an admin-role user to BYPASS the owner-session check. The
single-tenant Mini PC operator IS admin, so this restores the feature while preserving
multi-user isolation — a non-admin (member/guest) still cannot reach another user's owned
display, and shared displays (empty owner_session) remain readable by anyone authenticated.

Extract the authorization decision into a small PURE exported predicate
`canAccessDisplay({ownerSession, callerSession, callerRole})` so the admin-bypass / owner /
shared matrix is unit-testable without a full tRPC caller harness (mirrors the
config-router pattern of testing an extracted factory/predicate).

Purpose: make getVncUrl reachable for the admin operator on MCP-created displays so the live
VNC window and hover strip work end-to-end on the Mini PC.
Output: the `canAccessDisplay` predicate, its use in getVncUrl, an amended T-254-01 router
comment documenting the deliberate admin bypass, and a vitest covering the authz matrix.
</objective>
