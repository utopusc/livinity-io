<objective>
WS-B — The Caddy emit carve-out (the security spine). In `caddy.ts` `generateFullCaddyfile`, extend the SINGLE-USER
installed-app subdomain emit (the `else` branch at lines 575-611) so that when `sub.publicAccess` is present and
`mode !== 'none'`, the subdomain block is split into mutually-exclusive `handle` blocks:
- `paths` mode: one `handle <prefix>*` block PER public path prefix, each a `reverse_proxy` to `127.0.0.1:<port>`
  WITH the mandatory `request_header -Remote-User / -Remote-Role / -X-Daemon-Bearer` strip, followed LAST by the
  existing 256-04 gated catch-all `handle { forward_auth /auth/verify ... }` (UNCHANGED — same daemon-bearer +
  loopback Host/Origin rewrite for OpenDesign).
- `whole-app` mode: drop the gated catch-all entirely, emit a SINGLE header-stripped `handle { reverse_proxy ... }`
  (no forward_auth, no daemon bearer — the app relies on its OWN auth).
- `none` / absent: emit the EXACT current 256-04 gated block, byte-for-byte (SC5 regression).

The header-strip (`-Remote-User -Remote-Role -X-Daemon-Bearer`) is HARD-CODED into the public-block template and
emitted in EVERY public block unconditionally — it is NOT a configurable field on SubdomainConfig. The daemon
bearer (`upstreamBearer` → `header_up Authorization`) is emitted ONLY inside the gated catch-all, NEVER in a public
block.

Purpose: this is the inverse of 256/257 hardening — it lets chosen paths skip the login gate while making it
structurally impossible to leak the daemon bearer or spoofed identity headers onto a public route.
Output: the carve-out emit in generateFullCaddyfile + a test suite proving the spine (strip-always), the regression
(gated byte-equivalence), and both emit shapes.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| public internet → public handle block | an unauthenticated visitor reaches the container with NO LivOS session |
| client-supplied request headers → upstream | a visitor could inject Remote-User / X-Daemon-Bearer to spoof a privileged identity |
| app-author publicAccess.paths → generated Caddyfile | a hostile manifest path could attempt Caddyfile breakout |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-258B-01 | Spoofing / EoP | client injects Remote-User/Remote-Role on a public route to impersonate an authed user upstream | mitigate | `request_header -Remote-User -Remote-Role` hard-coded in EVERY public block — client-supplied identity headers are deleted before reverse_proxy (Task 1/2). Non-configurable. |
| T-258B-02 | Information Disclosure | the high-priv X-Daemon-Bearer leaks onto a public route | mitigate | `request_header -X-Daemon-Bearer` hard-coded in every public block; the bearer `header_up Authorization` is emitted ONLY inside the gated catch-all, never in a public block (Task 1 Test 4 / Task 2 Test 2). |
| T-258B-03 | Tampering | a malicious manifest publicAccess.path injects `}`/quote to break out of the Caddyfile | mitigate | per-prefix charset/skip guard (Task 1 step 3) mirrors the 257-06 safeBearer gate — whitespace/brace/quote prefixes are dropped, never interpolated. |
| T-258B-04 | EoP | a gated path falls through to a public block (booking carve-out too broad) | mitigate | Caddy first-match-wins + public handles emitted BEFORE the gated catch-all; the catch-all (`handle {` no matcher) stays LAST so any non-public path stays gated (Task 1 Test 5). |
