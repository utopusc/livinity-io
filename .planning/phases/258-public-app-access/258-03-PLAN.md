<objective>
WS-C — Hard guardrails (the security spine, server-side). Build the ONE source of truth for "this app may NOT be
made public", and enforce it at the API (not just the UI).

NOTE-2 (plan-checker — avoid a false guard): the LOAD-BEARING forbidden triggers are the signals the 257 WS-C
compose-sanitizer does NOT strip + the 256-04 daemon-bearer:
  1. `manifest.neverPublic === true`
  2. `manifest.requiresLocalAiClis === true`
  3. the 256-04 daemon bearer — `readAppDaemonToken(appId)` / the SubdomainConfig `upstreamBearer` is present.
These three are what actually protect OpenDesign / OpenHands-class apps, because the 257 sanitizer
(`sanitizeNonBuiltinCompose`, compose-sanitizer.ts:116-198) MUTATES the compose at install time: it `delete`s
`privileged` (:134), `delete`s `network_mode:host` (:140), `delete`s `pid:host`/`cap_add`, and THROWS
`ComposeRejected` on a docker.sock host-bind (:176-185). So an INSTALLED app's sanitized on-disk compose may NO
LONGER carry `privileged`/`network_mode:host`/docker.sock at all. The compose checks therefore CANNOT be the primary
guard for installed apps.
We KEEP the `docker.sock` / `privileged` / `network_mode:host` checks as DEFENSE IN DEPTH (they still catch a
compose that was never sanitized, or one read pre-sanitize), but the plan must NOT imply they are the primary guard.

WHICH COMPOSE (NOTE-2, explicit): `isPublicForbidden` is a PURE predicate — it forbids based on whatever compose it
is handed. The CALLERS decide which compose to read. For maximum safety the callers SHOULD pass the ORIGINAL
catalog/manifest compose (the un-sanitized source) when it is available, so the defense-in-depth signals are
meaningful; if only the sanitized on-disk compose is available, the three load-bearing triggers
(neverPublic/requiresLocalAiClis/daemon-bearer) still hold and are sufficient to protect the dangerous classes.
Task 1 documents this on the signal struct; Task 2/3 document which compose each call site passes.

An app is PUBLIC-FORBIDDEN if ANY trigger fires (load-bearing first, defense-in-depth second).

Three deliverables:
1. `public-forbidden.ts` — a pure `isPublicForbidden(signals)` predicate + a typed reason, the single policy module
   both the API gate and the subdomain-wiring import.
2. `routes.ts` — a `setPublicAccess` tRPC mutation that (a) resolves the caller's owner-or-admin authority, (b)
   calls `isPublicForbidden` and rejects with a 403 TRPCError for a forbidden app, (c) persists the per-install
   PublicAccessInstallSetting, and (d) triggers a runtime Caddy regen (no reinstall).
3. `apps.ts` — persistence helpers (get/setPublicAccessSetting on the same Redis store as the SubdomainConfig) +
   wire `registerAppSubdomain` to resolve the persisted setting via `resolvePublicAccess` and thread it onto
   `SubdomainConfig.publicAccess` — re-asserting `isPublicForbidden` so a forbidden app NEVER gets a public config
   persisted/emitted even if a stale setting exists.

Purpose: make the never-public guarantee structural and server-enforced — the inverse of 256/257 cannot be undone
by a UI bug, a forged request, or a stale config. Default stays private (opt-in only).
Output: the policy module + test, the gated mutation, and the wired registerAppSubdomain + persistence.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| tRPC caller → setPublicAccess mutation | a non-owner / non-admin could try to expose someone else's app |
| stale/forged persisted setting → registerAppSubdomain | a leftover public setting could try to expose a now-forbidden app |
| privileged app (docker.sock/bearer/host CLIs) → public toggle | exposing these would hand the daemon/host to the internet |
| sanitized on-disk compose → forbidden check | the 257 sanitizer may have stripped privileged/docker.sock, so the compose check alone is insufficient |
