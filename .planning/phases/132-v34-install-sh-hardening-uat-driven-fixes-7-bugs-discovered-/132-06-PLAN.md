<objective>
Fix Bug #7: After install completes, Caddy is left in `failed` state (from
prior install attempts on the same box) and never `reset-failed` + started.
TLS + DNS-01 wildcard cert acquired, Caddyfile valid (`caddy validate` →
`Valid configuration`), but Caddy daemon isn't running → port 443 unbound
→ `https://<domain>` returns HTTP 000.

Add explicit `systemctl reset-failed caddy && systemctl start caddy` to the
install flow, ideally in `deploy-livinityd.sh` (after the Caddyfile is
written + before the install completes banner), or in `mode-hybrid.sh`
(after the cert-acquisition step). Verify Caddy is `active` within 30s
(LE first cert can take 5-20s).
</objective>

<task id="06-01" type="execute">
<action>
Locate the section of `deploy-livinityd.sh` (or `mode-hybrid.sh`) that
writes the Caddyfile + reloads Caddy. Add a defensive
`systemctl reset-failed caddy` call BEFORE attempting to start/reload,
and a wait-for-active loop after.

```bash
# ── Phase 132-06: Caddy reset + start with active-wait ────────
# Without this, an install on a box where Caddy was previously failed
# (common: install retries, leftover prior partial installs) leaves
# Caddy in `failed` state — TLS + DNS work but port 443 is unbound.
info "Ensuring Caddy is started and reachable"
systemctl reset-failed caddy 2>/dev/null || true
systemctl daemon-reload
systemctl enable caddy 2>&1 | tail -3
systemctl restart caddy

# Wait up to 30s for Caddy to come active (LE first cert acquisition
# can take 5-20s on a fresh domain).
for i in {1..30}; do
    if systemctl is-active caddy >/dev/null 2>&1; then
        ok "Caddy active after ${i}s"
        break
    fi
    sleep 1
done

if ! systemctl is-active caddy >/dev/null 2>&1; then
    warn "Caddy did not reach active state in 30s. Tail logs:"
    warn "  journalctl -u caddy --no-pager -n 50"
    warn "Install will continue but HTTPS may be down until Caddy starts."
fi
```

Place this AFTER the Caddyfile write step + AFTER all DNS/cert prep, but
BEFORE the final "install complete" banner.
