<objective>
Rewrite the spawn body inside `WebAppWindowManager.spawn()` so it talks to the already-booted Chrome (via `ChromeCdpClient` from 101-01) instead of launching a per-WebApp `--app=URL` child. The surrounding scaffolding — idempotency check, per-user cap, MCP-config registration, broadcastActiveWid, stream-start, map insertion — stays unchanged. Close paths also route through CDP so port releases line up with target lifetime.

Wid resolution algorithm (RESEARCH.md Open Question #1 RESOLVED):
```
1. Snapshot baselineWids = xdotool search --pid <chrome-pid> BEFORE CDP createTarget
2. Call chromeCdpClient.createWindowForUrl(url, bounds)
3. Poll xdotool search --pid <chrome-pid> AFTER createTarget; first wid in (current - baseline) is ours
```
This is xdotool poll but PID-narrowed: deterministic, no title-match race. The OLD `findNewWindowMatching({titleHints, baselineWids, timeoutMs})` is REPLACED by the new `findNewWindowByPid({chromePid, baselineWids, timeoutMs})` — the brittle title-hint match is GONE.

Purpose: Pillar A demands one Chrome process with N top-level windows under a shared `--user-data-dir`. The current `--app=URL` argv path IPC-merges into the singleton (100-10-08 root cause), so only the first window appears. CDP `Target.createTarget({newWindow:true})` is the only way to get distinct windows under a shared profile. Title-match was the source of the "wrong window picked up by x11vnc" race (100-10-08 carryover); PID-narrowed lookup eliminates it.

Output: WebApps open as distinct CDP targets with distinct X11 wids; the `--app=URL` argv path is gone from `window-manager.ts`; `findNewWindowMatching` is gone from `window-manager.ts` (replaced by `findNewWindowByPid`).
</objective>
