<objective>
Close the architectural gap where WebApp Xvfb displays are spawned but never written to the display registry. Inject `displayManager` into `WebAppWindowManager`; on `spawn()` call `registerExisting` (owner = the WebApp user) so the `:N` appears in `displays.list`; on `close()` call `kill`. Use `registerExisting` (NOT `create` — the Xvfb already exists) and give webapps a disjoint allocator range so they can never collide with MCP `create()` within one boot.

Purpose: D-255-WEBAPP-REGISTER — installed WebApps become listable displays in the popover, correctly isolated per user.
Output: spawn/close registry lifecycle + disjoint range, all backend tests green.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| WebApp spawn (user-initiated) → Redis display registry | A user's WebApp writes a display record that other users must NOT see |
| displayManager.kill → Redis | Only the owning session may delete its record |
| webapp allocator ↔ MCP create() allocator | Two independent allocators share one Redis `:N` namespace |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-255-07 | Information disclosure | user B seeing user A's WebApp display in their popover | mitigate | spawn writes `ownerSession: opts.userId` (NOT ''). `displays.list` returns all, but `displays.screenshot`/`getVncUrl` gate on `canAccessDisplay` — a non-admin cannot screenshot/open a foreign owner's display. Owner isolation preserved end-to-end. |
| T-255-08 | Tampering | one user killing another user's display record | mitigate | `kill` gates on `owner_session === callerSession` (display-manager.ts:407). close() passes `callerSession: entry.userId` (the owner), so only the owner's own teardown deletes the record. |
| T-255-09 | Tampering/DoS | webapp + MCP create() both claiming the same `:N` ("server already active for display N") | mitigate | Disjoint allocator ranges: webapps [10,60) via registerExisting (no allocator advance), MCP create() floor 60. A unit test asserts no overlap. registerExisting is Redis-only (no Xvfb spawn) so it cannot double-spawn. |
| T-255-10 | Denial of service | a Redis write failure aborting a WebApp launch | mitigate | registerExisting/kill are best-effort try/catch (non-fatal warn) — a registry write failure never breaks spawn/close. |
| T-255-11 | Repudiation | unclear which user owns a registered display | accept | owner_session = userId is recorded in Redis; existing display-manager logging covers it. No additional audit needed for single-tenant operator box. |
</threat_model>
