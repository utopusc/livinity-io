<objective>
Add a cross-tab / cross-device "attached elsewhere" indicator so the user knows when the same CC session is open in another browser tab. Implemented via Redis pub/sub on a single channel `liv:cc-pty:attached` plus a tRPC subscription. The badge is purely informational — concurrent attach is still allowed (D-V35-E mirror mode).

Purpose: Close the v35.0 cross-tab UX gap. With Phase 166's mirror-mode attach, two tabs CAN attach to the same tmux session simultaneously and both see live output. Users need to know this is happening so they don't accidentally type into both windows.

Output: Additive Redis publish on attach/detach, new tRPC subscription procedure, SessionSidebar consumes the subscription, SessionItem badge wiring.
</objective>

    2. Append a 6th procedure to the router:

       ```ts
       // Phase 168-04 — Cross-tab attach status subscription. Streams
       // {sessionId, attachId, attachedAt, action} JSON envelopes published on
       // 'liv:cc-pty:attached'. UI consumers compute attachedElsewhere by
       // comparing payload.attachId to their local tab's attachId.
       //
       // Note: subscription routes over WS by design (the WHOLE POINT of
       // subscriptions is server-push). It does NOT belong in httpOnlyPaths.
       subscribeAttachStatus: adminProcedure.subscription(({ctx}) => {
           return observable<{
               sessionId: string
               attachId: string
               attachedAt: number
               action: 'attached' | 'detached'
           }>((emit) => {
               // Duplicate the Redis client because subscribe-mode connections
               // can't run normal commands (ioredis idiom).
               const sub = ctx.livinityd!.ai.redis.duplicate()
               sub.subscribe('liv:cc-pty:attached').catch((err) =>
                   ctx.livinityd!.logger.error('[cc-pty] subscribe failed', err),
               )
               const onMessage = (channel: string, msg: string) => {
                   if (channel !== 'liv:cc-pty:attached') return
                   try {
                       const parsed = JSON.parse(msg)
                       if (
                           typeof parsed.sessionId === 'string' &&
                           typeof parsed.attachId === 'string' &&
                           typeof parsed.attachedAt === 'number' &&
                           (parsed.action === 'attached' || parsed.action === 'detached')
                       ) {
                           emit.next(parsed)
                       }
                   } catch {
                       /* malformed payload — silently drop */
                   }
               }
               sub.on('message', onMessage)
               return () => {
                   sub.off('message', onMessage)
                   sub.unsubscribe('liv:cc-pty:attached').catch(() => {})
                   sub.quit().catch(() => {})
               }
           })
       }),
       ```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CcPtyManager → Redis publish | Internal trust; payload is server-constructed JSON. |
| Redis → tRPC subscription | Internal trust; payload validated by shape-check in subscription. |
| tRPC subscription → browser tab | Per-user JWT; subscription is adminProcedure-gated; userId filter applied in onMessage handler. |
| browser tab attachId → server | Untrusted; opaque string, never used for authorization. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-168-04-01 | S (Spoofing) — attachId collision/forgery | client-generated attachId | accept | attachId is a uuid v4 (or fallback random) used purely as a self-identification token for "is this me or another tab?". It is NEVER used for authorization. Even if forged, the worst outcome is a peer tab incorrectly suppressing its own badge — no privilege escalation. |
| T-168-04-02 | I (Info disclosure via pub/sub channel) — PII leakage | Redis channel content | mitigate | Schema enforced in `onMessage` shape-check: payload MUST be `{sessionId, attachId, attachedAt, action}` with `action ∈ {'attached','detached'}`. No session content, no userId, no jsonl. Server `publish` calls hard-code these 4 fields (no spread, no extra metadata). |
| T-168-04-03 | I (Cross-user info disclosure) — sessionId leak across users | Subscription forwards all channel messages | mitigate | `onMessage` calls `ccPtyManager.getSession(sessionId)` and suppresses emit if `session.userId !== ctx.currentUser.id`. Defense-in-depth even in single-user mode. T-168-01-03 also gates the upstream `list` so sessionIds the caller doesn't own are unknown to them anyway. |
| T-168-04-04 | T (Tampering) — pub/sub channel name collision with another LivOS subsystem | hard-coded constant | mitigate | Channel name `liv:cc-pty:attached` is namespaced under `liv:cc-pty:*` (consistent with Phase 65-03 capability registry prefix migration; grep `liv:cc-pty:` in the repo confirms NO prior collision). New channels added later MUST stay under this prefix. |
| T-168-04-05 | D (Denial of service) — runaway publish under attach storm | publish per attach/detach | accept | Each session has bounded mirror attachers (CONTEXT.md does not cap; D-V35-E is unrestricted but practical UI limit is ~5 tabs per user). Publish-per-event is O(1). Redis can absorb thousands of publishes/sec; even an adversarial user can't exceed the `maxSessions=10` cap (Phase 166-03), so total event rate is bounded by 10 sessions × ~1 attach/sec = 10 ops/sec worst case. Acceptable. |
| T-168-04-06 | R (Repudiation) — destructive detach without record | publish-on-detach | accept | Manager already logs `[cc-pty]` lines for attach/kill (Phase 166-03 line 243). Publish is a UX feature, not an audit feature. v37 multi-user audit will add an `audit_events` table entry per attach if needed. |
| T-168-04-07 | E (Elevation) — malformed JSON on channel crashes server | onMessage parser | mitigate | `try { JSON.parse(msg) } catch { return }` — malformed messages silently dropped. Shape-check rejects payloads that don't have the four required fields. Assertion S5 verifies. |
| T-168-04-08 | I (Info disclosure via timing) — peer tab sees the EXISTENCE of another session attachment | subscription forwards `{sessionId, attachId, action}` | accept | Single-user mode: the attacker is the user themselves; nothing to hide. Multi-user (v36+): T-168-04-03 mitigation suppresses cross-user emits. Acceptable. |
| T-168-04-09 | D (Denial of service) — Redis subscriber leak on subscription disconnect | observable cleanup | mitigate | Observable teardown function calls `sub.off('message', onMessage)`, `sub.unsubscribe(...)`, `sub.quit()`. Each subscription owns ONE duplicated ioredis connection; quit on teardown releases the underlying socket. Assertion S3 verifies. |
