Redis lock pattern (ioredis):
```typescript
// Acquire (NX = only if not exists, PX = TTL in ms)
const acquired = await redis.set(
  `liv:agent:running:${agentId}`,
  runId,
  'NX', 'PX', 900_000  // 15 min TTL
)
// acquired === 'OK' means we have the lock; null means already held
// Release in finally:
await redis.del(`liv:agent:running:${agentId}`)
```

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| agentId input → Redis lock key | agentId from MCP tool input or scheduler; forms Redis key |
| vaultRoot + agentId → filesystem path | Must not escape vaultRoot/items/ tree |
| CcPtyManager userId | Hardcoded as 'scheduler' — never caller-supplied |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-177-02-01 | Denial of Service | Redis lock | mitigate | NX + PX 900000 TTL — lock auto-expires after 15 min so a crashed run cannot block the agent permanently |
| T-177-02-02 | Tampering | inbox file path (agentId in path) | mitigate | agentId validated upstream by ItemStore.get() — store uses ID_RE `/^[0-9A-Za-z_-]{20,}$/`; no path traversal possible |
| T-177-02-03 | Elevation of Privilege | CcPtyManager userId | mitigate | userId hardcoded as `'scheduler'` — never derived from caller input; CcPtyManager's USER_ID_RE validates it on session create |
| T-177-02-04 | Information Disclosure | inbox frontmatter | accept | Inbox files visible to vault owner (local filesystem); no network exposure; contain only run metadata (no secrets) |
</threat_model>
