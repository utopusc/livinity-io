- **Option A selection:** The 226-03 DEPLOY-LOG surfaced three options (A: inline emit; B: inline emit + drop snippet file; C: hybrid emit + keep snippet + installer). This plan implements Option A (recommended). Option B was rejected because keeping the snippet file as reference documentation has zero runtime cost and preserves the directive shape as a paper trail. Option C was rejected because it adds two coupling points (top-level `import conf.d/*.caddy` + in-block `import liv_assistant`) where one inline handler suffices.
- **Caddy v2 multi-path pitfall (Phase 218 T1):** `handle_path` accepts ONE matcher only. We use `@liv path /liv /liv/*` + `handle @liv` + `uri strip_prefix /liv` (the canonical multi-path idiom). The LIV_ASSISTANT_HANDLE constant has an explicit comment block documenting this so future maintainers don't "simplify" it back to `handle_path /liv*`.
- **WebSocket auto-upgrade:** Caddy v2's `reverse_proxy` auto-handles `Upgrade: websocket` and `Connection: upgrade` headers. We deliberately do NOT set `header_up Connection` / `header_up Upgrade` directives that would strip the WS handshake. AionUi (Phase 222 spike + Phase 223 ship) uses WS for chat streaming. The vitest test asserts these directives are absent (negative assertion).
- **CSP override mechanics:** `header_down -X-Frame-Options` strips XFO outbound. `header_down -Content-Security-Policy` strips upstream CSP. Then `header Content-Security-Policy "frame-ancestors 'self' https://bruce.livinity.io"` at `handle` scope (one level OUT from reverse_proxy) sets the new CSP AFTER the upstream's was stripped. The CSP allows the LivOS shell on `https://bruce.livinity.io` (Phase 227 iframe mount) to embed, and `'self'` covers the embedded service navigating itself.
- **livinityd `tsx` runtime:** package.json `"main": "./source/index.ts"` + scripts `start: "./source/cli.ts"`. livinityd runs TypeScript directly via tsx — no compiled artifact path that update.sh needs to refresh. Mini PC `systemctl restart livos.service` is sufficient to pick up the new caddy.ts.
- **Why Task 3 is `checkpoint:human-verify` not `auto`:** Even under autonomous chain, a real Mini PC deploy with 6 external SC measurements + DEPLOY-LOG authoring is the natural integration point where a human sanity-check belongs. The auto-chain rule auto-approves this checkpoint IF and ONLY IF the executor produces a DEPLOY-LOG.md with all 6 SCs GREEN. Any RED SC blocks auto-approval and surfaces for human review.
- **226-03 BLOCKED context preserved:** This plan deliberately does NOT revert commits `bef03544` (Plan 226-02 update.sh wiring) or `1e56b8c9` (Plan 226-02 SUMMARY). They stay on master as the audit trail of the original (architecturally-doomed) approach. The deprecation stub + REFERENCE ONLY header are the "soft retirement" of those artifacts. If a future maintainer wonders why the installer is a stub, they can read this plan + 226-03 DEPLOY-LOG to understand the recovery path.
- **Mini PC SSH rate limit:** Per `feedback_ssh_rate_limit`, batch all read-only commands into ONE ssh invocation. The deploy task does this via the 6 batched-SSH structure (preflight + RUN 1 + RUN 2 + post-deploy validate — 4 invocations total, well below fail2ban threshold).

Both are delivered by this plan. Phase 227 can plan immediately after this plan SHIPS.
