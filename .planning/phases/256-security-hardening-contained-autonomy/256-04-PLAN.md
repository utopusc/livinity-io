WS-D — Auth Fail-Closed. Close LIVOS-004 (deactivated/deleted user with a valid JWT is silently promoted
to legacy admin because `requireRole` treats absent `currentUser` as single-user admin), LIVOS-008 (the
Caddy subdomain gate is cookie-PRESENCE-only — any `LIVINITY_SESSION=<garbage>` unlocks gated apps), and
LIVOS-014/018/019/025 (liv-core port 3200 + the memory API fail OPEN when `LIV_API_KEY` is unset — auth
silently disabled, exposing the agent-RCE surface). Per the operator-locked decision: throw on
inactive/deleted users and never treat "no resolved currentUser" as admin; make the subdomain gate
validate the JWT via a livinityd forward_auth endpoint; make the liv-core + memory key middleware fail
CLOSED.

Purpose: disabling a user actually revokes access (and never escalates them), forged-cookie requests are
rejected at the gate, and an env/deploy regression that drops LIV_API_KEY refuses traffic instead of
exposing unauthenticated agent execution.
Output: a fail-closed `is-authenticated.ts`, a `/auth/verify` forward_auth endpoint + Caddy gate rewrite,
and fail-closed `requireApiKey`/`verifyApiKey` in liv-core and memory.

SERVICE-TOKEN PRESERVATION (revision fix E): the LIVOS-004 fix must reject deactivated/deleted *user JWTs*
WITHOUT regressing the legitimate X-Api-Key service-token path (openclaw / loopback gateway plugin). That
path (is-authenticated.ts :44-57) currently `next()`s WITHOUT a currentUser when `getAdminUser()` throws
(legacy single-user, no DB). With the new requireRole "absent currentUser is NOT admin" rule, that
fall-through would become FORBIDDEN — a regression. Fix: in the service-token `catch` (no-DB) branch, set
`ctx.legacySingleUser = true` (the admin-equivalent marker requireRole now honors) so the service path stays
authorized. Only USER-JWT failures (userId present but inactive/missing) throw.
