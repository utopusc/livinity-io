# Phase 103.1 — Master Chrome Hot-Fix + Luse Cross-Display Aggregation

## Trigger

Phase 103 deployed to Mini PC at SHA `c89f7139` (2026-05-11). User-walked UAT
on real hardware surfaced two regressions that the unit-test suite could not
catch.

## Bugs fixed

### Bug 1 — Master Chrome WebSocket 1006 (TWO-cause stack)

This was a 2-layer bug. Both layers had to ship for the user-facing symptom
(WS 1006 on every Open) to clear. Layer A surfaced on every retry-after-crash
loop; layer B surfaced on every clean spawn. Commit `37f0bfb4` shipped fix A;
commit `e531b3c4` shipped fix B after live UAT on the Mini PC showed the
symptom persisting despite locks being cleaned (verified via tRPC curl —
`chromeMaster.status.running` was still `false` 30s after a successful
`startLogin` return).

#### Layer A — stale Chromium singleton lock

**Symptom (browser console):**

```
WebSocket connection to 'wss://bruce.livinity.io/ws/stream/ffffafca-...' failed
Failed when connecting: Connection closed (code: 1006)
```

**Mini PC livinityd log:**

```
15:04:52 stream ffffafca... started (display=:14 rfbPort=15909)
15:04:52 stream ffffafca... x11vnc exited cleanly (stop requested)
15:04:52 stream ffffafca... stopped (vnc, display=:14)
15:04:52 [tunnel] /ws/stream/ffffafca-...: Unexpected server response: 404
```

**Root cause:** Stale Chromium process-singleton lock artifacts
(`SingletonLock` + `SingletonCookie` + `SingletonSocket`) left in
`/opt/livos/data/chrome-master` by a prior crashed master Chrome session.
Chromium's `process_singleton_posix.cc` reads them, attempts to message the
embedded dead PID, and the new instance exits with code != 0. That fires
`chrome.on('exit')` → `cleanupMaster()` → `stopStream()` → stream is gone by
the time the client WS upgrade hits `/ws/stream/{id}` → 404 → 1006 in browser.

Confirmation: user clicked Reset (which wipes the master profile dir entirely),
then clicked Open again — stream `3dfd77f6` on `:18` ran 52s with a clean RFB
handshake. The wipe path bypassed the lock; the spawn path could not.

**Fix:** `clearStaleSingletonLocks(MASTER_PROFILE_DIR, unlinkFn, logger)`
called after `profileSeeder.ensureMasterExists()` and before
`chromeSpawnFn()` in `chromeMaster.startLogin`. Unlinks the three artifacts;
ENOENT is the happy path; non-ENOENT errors are logged but non-fatal (no
regression vs pre-103.1 if cleanup itself fails — Chrome will hit the same
lock and the user sees the same pre-fix bug, no worse).

Files: `chrome-master/master-login-routes.ts` + `master-login-routes.test.ts`.

Commit: `37f0bfb4` `fix(103.1): clear stale Chromium singleton lock files`.

Tests: 3 new — invocation paths, ENOENT swallow, EPERM swallow.

#### Layer B — chrome daemonization mis-classified as crash

**Symptom after layer A shipped (verified live on Mini PC via tRPC curl):**
The stale-lock cleanup ran (verified — fake locks I injected got removed),
Chrome spawned successfully (`pid:1132665, display:":10"`), stream registered
(`stream e2462d48 started`)... and then `(stop requested)` fired in the SAME
second. `chromeMaster.status` 30 seconds later returned `running:false`.

**Root cause:** `chromeMaster.startLogin` watches `chrome.child` — the
`sudo -n -u bruce google-chrome ...` wrapper process — for an `exit` event.
Google Chrome forks itself into the background on startup; the launcher
(the binary `sudo` execs) exits with `code=0`. Pre-103.1 the exit handler
treated ANY exit as a crash and ran the `cleanupMaster()` cascade:
`stopStream → x11vnc.kill → chrome.stop → xvfb.stop → release allocators`.
That ran within ms of `startStream` returning, so by the time the client's
browser opened its WebSocket to `/ws/stream/{id}`, the stream had already
been removed from `streamManager.streams`. The WS handler returned 404 →
browser surfaced as `code=1006 abnormal closure`.

**Fix:** Filter the exit signal:

```ts
chrome.child.on('exit', (code, signal) => {
  if (code === 0 && signal === null) return  // daemonization (no-op)
  void cleanupMaster()                        // real crash or kill
})
```

- `code=0 + signal=null` → daemonization parent's clean exit (no-op, the
  actual Chrome continues running detached on its Xvfb).
- `code!=0` → real crash (cleanup as before).
- `code=null + signal != null` → SIGTERM/SIGKILL (cleanup as before).

**Trade-off (accepted):** A post-daemonization Chrome crash will not be
auto-detected because the launcher already returned. Recovery path: user
clicks "Close Master Chrome" which calls `cleanupMaster` explicitly. A
future patch could poll the actual Chrome PID via /proc; out of scope for
this hot-fix.

Commit: `e531b3c4` `fix(103.1-2): chrome exit watcher ignores code=0 daemonization`.

Tests: Test 15 updated to use code=11 (non-zero crash). New Test 15b verifies
code=0+null path is no-op. New Test 15c verifies SIGTERM still cleans up.
24/24 master-login tests green (was 22/22 pre-103.1-2).

### Bug 2 — `list_windows` misses windows on per-WebApp displays

**Symptom:** From a global chat, user asked "find Dinkytown open". Agent
called `list_windows` → response: `1 window: New Tab - Google Chrome 1920x1080`.
`1920x1080` is the host display resolution; per-WebApp Xvfb is 1280x720.
Dinkytown WebApp on `:11` was invisible.

**Root cause:** Phase 103-04 prompt prescribes `display: ":N"` per call IF
the agent has an `activeDisplay` context. From a global chat there's no
WebApp context, so the agent omitted `display:`. Phase 103-05 default-off
left the global luse MCP as the single MCP serving all displays — its
`defaultDisplay = WEBAPPS_X11_ENV = ":1"`. So the call scoped to `:1`
and never touched `:11`+.

**Fix:** When `list_windows` is called with NEITHER an explicit `display`
arg NOR a server-level `defaultDisplay` (i.e. the global luse MCP serving
a generic roster query), aggregate across every active X11 display
discovered via `/tmp/.X11-unix/X<N>` socket scan. Each result row carries
its own `display` field (existing `ListWindowsExtended` shape from
`native/window.ts`), so the agent can dispatch follow-up `click`/`type`/`focus`
calls with the correct `display: ":N"` arg.

Per-WebApp Luse MCP (defaultDisplay set) stays scoped — no behavior change.
Explicit `display:` arg stays scoped — no behavior change. `:0` excluded
(Mini PC is headless; no physical screen → no socket).

Tool description also updated to tell the agent that omitting `display:`
yields a cross-display roster.

Files: `computer-use/mcp/tools.ts` + `tools.test.ts` + `luse-tools.ts`
(schema description).

Commit: `d634ffe4` `fix(103.1): list_windows aggregates across all active X11 displays`.

Tests: 44/44 mcp tools (5 new — aggregation happy path, scoped-with-arg,
scoped-with-default, `:0` exclusion, mid-scan fault tolerance).

Test seam: `__setReaddirForTest()` exported from `mcp/tools.ts` lets vitest
inject a fake readdir since `vi.spyOn` cannot rewrite ESM-frozen
`node:fs/promises.readdir`.
