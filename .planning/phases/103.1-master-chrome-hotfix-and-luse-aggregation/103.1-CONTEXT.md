# Phase 103.1 — Master Chrome Hot-Fix + Luse Cross-Display Aggregation

## Trigger

Phase 103 deployed to Mini PC at SHA `c89f7139` on 2026-05-11. User-walked UAT
(informal first attempt) surfaced two regressions in actual Mini PC behavior
that the unit-test suite could not catch:

### Bug 1 — Master Chrome WebSocket 1006 on first Open

User clicked **Open Chrome Profile**. Stream registered, then immediately
unregistered. Browser console showed `WebSocket failed (code: 1006)` and
`Connection closed (code: 1006)`. The Master Chrome panel rendered the noVNC
viewer shell but the stream surface stayed blank.

Root cause (confirmed via `journalctl -u livos`):

```
15:04:52 stream ffffafca... started (display=:14 rfbPort=15909)
15:04:52 stream ffffafca...: x11vnc exited cleanly (stop requested)
15:04:52 stream ffffafca... stopped (vnc, display=:14)
15:04:52 [tunnel] Local WS error for livos:8080/ws/stream/ffffafca-... Unexpected server response: 404
```

The stream got `(stop requested)` within the same second it started. Calling
`chromeMaster.cleanupMaster()` is the only path that triggers this — it fires
via `chrome.child.on('exit', cleanupMaster)`. So Chrome exited within ms of
spawn, which fired the exit listener, which stopped the stream, which made the
client's WS attempt 404.

Why Chrome exits within ms of spawn: stale **Chromium process-singleton lock
files** in `/opt/livos/data/chrome-master/` (`SingletonLock`,
`SingletonCookie`, `SingletonSocket`). When the previous master Chrome session
crashed or got SIGKILLed without clean shutdown, these files persist. Chromium's
`process_singleton_posix.cc` reads the embedded PID, attempts to send to it
(the PID is dead), and the new instance exits with `cannot acquire singleton
lock` and code != 0.

User confirmation: after clicking Reset (which deletes the master profile dir
entirely) and clicking Open again, stream `3dfd77f6-...` on `:18` ran for 52s
with a clean RFB handshake (1280x720, JPEG quality 6). The reset path bypassed
the stale-lock problem by wiping the dir.

### Bug 2 — Luse list_windows misses windows on other displays

User asked the agent (in chat) to "Find Dinkytown open". Agent called
`list_windows`. Response showed `1 window: New Tab - Google Chrome 1920x1080`.

`1920x1080` is the **host display** resolution (`:1` — `WEBAPPS_X11_ENV` set
by Phase 100-08). The Dinkytown WebApp lives on its own per-app Xvfb display
(e.g. `:11`, 1280x720). The agent's chat was opened from a global context (not
from inside the Dinkytown window), so no `activeDisplay` snippet was injected,
so the agent omitted `display:` from the `list_windows` call, which fell back
to `LUSE_DISPLAY` env (`:1`).

Phase 103-04 prompt update prescribes `MUST pass display: ":N"` per tool call,
but only when an `activeDisplay` is known. For roster queries from a global
chat, the agent needs to enumerate across all active displays.
