# Phase 100 Plan 09-07: Fluxbox Stderr Capture + xdotool Window-Discovery Fallback Summary

**One-liner:** Defense-in-depth fix for the user-reported "stream area inside WebApp window renders `wmctrl -lG: Cannot get client list properties (_NET_CLIENT_LIST or _WIN_CLIENT_LIST)` instead of Chrome content" bug. Layer 1 stops fluxbox from dying silently (piped stderr + 500ms health check + loud `logger.error` + thrown Error carrying the real stderr). Layer 2 makes `listAllWindows()` survive a missing WM by falling back to `xdotool search` + per-wid `getwindowgeometry --shell` / `getwindowname` (X11 tree walk, no EWMH atoms required). All 21 unit tests PASS (6 new + 15 pre-existing).

## Root cause

The user's 2026-05-10 bug report described the broken stream window rendering this string instead of Chrome content:

```
wmctrl -lG: Cannot get client list properties. (_NET_CLIENT_LIST or _WIN_CLIENT_LIST)
```

Tracing back through the call chain established by Phase 100-08:

1. The WebApp Window Manager calls `listAllWindows()` (from `window-discovery.ts`) to find the Chrome window we just spawned, to compute its geometry, etc.
2. `listAllWindows()` shells out to `wmctrl -lG`.
3. `wmctrl -lG` reads the `_NET_CLIENT_LIST` atom off the X11 root window. That atom is published by the running window manager — on the WebApp display (`:1`), that's the fluxbox helper added in Phase 100-08-01.
4. If no WM is running on `:1`, the root window has no `_NET_CLIENT_LIST` atom, and `wmctrl` prints the exact error string above to stderr and exits non-zero.

Why was fluxbox not running on `:1`? Reading `fluxbox-wm.ts:62-66` from Phase 100-08-01:

```ts
const child = spawnFn('sudo', args, {
  detached: true,
  stdio: 'ignore',                 // ← SWALLOWS STDERR
  env: {...process.env, DISPLAY: display},
}) as ChildProcess
```

`stdio: 'ignore'` discards both the child's stdout and stderr. If `sudo -n -u bruce fluxbox` failed at startup — sudo NOPASSWD for `bruce` not configured, `fluxbox` not in sudo's reset PATH, `:1` unreachable, etc. — the child died with whatever diagnostic message that **would** have been printed (e.g. `sudo: a password is required`, `sudo: fluxbox: command not found`) discarded into `/dev/null`. The `startFluxbox` promise still resolved with a "handle" pointing at a corpse pid. The launcher continued thinking it had a WM, and downstream `wmctrl -lG` calls failed with the EWMH error that surfaced where the stream UI should have rendered.

Sacred SHA `f3538e1d811992b782a9bb057d1b7f0a0189f95f` was not implicated — this was strictly a fluxbox-helper / window-discovery defect introduced in Phase 100-08-01.

## Fix shipped

Two layers of defense — neither alone fully closes the issue, but together they make the failure mode loud AND survivable:

### Layer 1 — fluxbox-wm.ts: stderr capture + 500ms health check

| Change | Before | After |
| --- | --- | --- |
| spawn stdio | `'ignore'` | `['ignore', 'pipe', 'pipe']` |
| stderr handling | discarded | accumulated to `stderrChunks: string[]` + `logger.warn(\`fluxbox stderr: ${text}\`)` per chunk |
| startup check | none | 500ms race: `setTimeout` vs `child.once('exit')`. If exit wins, `logger.error(...)` + `throw new Error(\`fluxbox failed to start on ${display}: ${stderr || 'no stderr output'}\`)` |

The `exited` promise is still wired to the original `child.on('exit')` listener so existing post-startup death detection keeps working.

Result: deploys where fluxbox can't start now produce a stack-traced error containing the actual sudo / PATH / X11 failure reason at the moment the caller awaits `startFluxbox()`. The error propagates up to the launcher caller and the systemd log instead of being silently consumed.

### Layer 2 — window-discovery.ts: xdotool fallback

Catch clause for `wmctrl -lG`:

```ts
} catch (err) {
  const e = err as NodeJS.ErrnoException & {stderr?: string}
  if (e.code === 'ENOENT') return []                 // pre-existing graceful empty
  const errText = String(e.stderr ?? '')
  if (errText.includes('Cannot get client list')
      || errText.includes('_NET_CLIENT_LIST')) {
    return listAllWindowsViaXdotool()                // ← NEW
  }
  throw err
}
```

`listAllWindowsViaXdotool()` (new private function):

1. Runs `xdotool search --name ''` — the empty regex matches every window, returning one decimal wid per line.
2. Per wid, runs `xdotool getwindowgeometry --shell <hex>` and `xdotool getwindowname <hex>` in parallel (per-call 1000ms timeout, individual `.catch` so a vanished window doesn't kill the whole list).
3. Parses the `--shell` key=value output via new `parseXdotoolShellGeom()` (covers `X=`, `Y=`, `WIDTH=`, `HEIGHT=`; returns `null` if any are missing).
4. Returns an array of `WindowInfo {wid, title, geometry}` — same shape as the wmctrl path, so all downstream callers are agnostic to which path was taken.

If both wmctrl AND xdotool fail (`ENOENT` or any other error in the xdotool path), returns `[]` — matches pre-existing graceful-empty semantics.

Result: even if fluxbox refuses to come up — say, on a freshly-provisioned Mini PC where the sudo NOPASSWD rule hasn't been added yet — the window manager keeps functioning. Per-WebApp launching, screenshot scoping, click routing, etc. all keep working. The fluxbox-helper error from Layer 1 still surfaces in logs, so the operator can fix sudo at their convenience without WebApps being broken in the meantime.

## Deviations from Plan

One minor delta — Rule 1 / test ergonomics:

1. **[Rule 1 - Bug] T-09-07-F2 fake-timer rejection observation.** The plan's <interfaces> sketch did not specify how the test would observe the rejection of `startFluxbox()` while also advancing fake timers. The first attempt called `await expect(startP).rejects.toThrow(...)` which interacts badly with `vi.useFakeTimers()` — the timeout-driven race never resolved because the test was already awaiting the rejection assertion, leading to a 5000ms test-level timeout. Fixed by attaching `.catch()` synchronously immediately after the spawn call (`const rejection = startP.catch((e) => e)`) so the rejection observation runs alongside the fake-timer advancement instead of blocking it. This is a test-infrastructure adjustment; the production code matches the <interfaces> spec verbatim.
