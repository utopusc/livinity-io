# Phase 100-09-03 SUMMARY

**One-liner:** Bytebot mouse moves now walk a smooth ~100ms trajectory (20 linear-interpolated xdotool mousemove --sync steps × 5ms inter-step sleep, selfclaude pattern) before each click, replacing the pre-09-03 teleport. Closes 100-09 Bug 3.

**Date completed:** 2026-05-09
**Sacred SHA gate:** PASSED (byte-identical pre + post all 3 commits).

## Goal

After this plan ships, every bytebot click that includes coordinates emits a sequence of xdotool mousemove --sync spawns (linearly interpolated between current cursor and target, default 20 steps × 5ms = ~100ms) BEFORE the focused click chain. Visual effect on the WebApp stream: the cursor walks naturally to the target rather than teleporting in one X11 frame.

This closes Bug 3 from 100-08 deploy live test ("mouse moves are jerky/teleport") and aligns LivOS bytebot's perceived behaviour with the selfclaude reference implementation (https://github.com/utopusc/selfclaude — README documents the same interpolation pattern for natural cursor movement).

## Root cause

`tryXdotoolClick` (input.ts pre-09-03) built a single xdotool argv batch:

```
windowactivate --sync <wid> windowfocus --sync <wid> mousemove --window <wid> --sync X Y click --clearmodifiers <btn>
```

xdotool processes `mousemove --sync X Y` as an instant warp — the cursor TELEPORTS to (X, Y) in one X11 frame. There's no perceived motion.

`moveMouse` had the same problem (`mouse.setPosition` from nut-js OR `xdotool mousemove --sync` both teleport), but moveMouse is the one-shot interactive cursor warp surface; out of scope for 09-03 (Carryover note below).
