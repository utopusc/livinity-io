## Privilege gate (G-100-10-E)

`mcp__luse__create_stream` is the only stream tool with a privilege gate. The gate semantics:

| State | Result |
|---|---|
| `liv:config:luse_can_create_streams` is the exact string `"true"` | Handler proceeds — calls `streamManager.startStream(...)`. |
| Key is unset (`redis.get` returns `null`) | Handler returns `isError:true` with message `Error: luse_can_create_streams disabled (set Redis liv:config:luse_can_create_streams=true to enable)`. |
| Key is any other string (`"false"`, `"1"`, `"yes"`, ...) | Same as unset — strict equality with `"true"` only. |
| `redis.get` throws (Redis connection down) | Handler treats as denied (`canCreate = false`) — same fail-closed semantics. |
| `redis` client is `null` (LUSE_REDIS_URL was missing in env) | Same fail-closed deny. |
| `streamManager` is `undefined` in options | Tool is NOT registered at all (opt-in pattern). Schema entry remains in LUSE_TOOLS for agent enumeration but the handler doesn't exist. |

**Operator enable (dev):**
```bash
redis-cli SET liv:config:luse_can_create_streams true
# OR remotely:
ssh bruce@10.69.31.68 'redis-cli -a "$(grep ^REDIS_URL /opt/livos/.env | cut -d@ -f1 | rev | cut -d: -f1 | rev | sed s/%21/!/)" SET liv:config:luse_can_create_streams true'
```

**Production posture:** key remains UNSET. The gate is intentionally fail-closed because a stream-creation tool exposes new network listeners under LLM control. Operators flip the flag only after threat modelling.

`mcp__luse__list_streams` has NO privilege gate — read-only + user-scoped via the existing `streamManager.listStreams({userId})` filter (D-93-06 ownership lookup).

## Redis wiring (plan-checker BLOCKER 3 fix)

The MCP server runs in its OWN Node.js process spawned by livinityd's `McpClientManager`. It CANNOT share the parent livinityd's ioredis instance (different process address spaces). The locked wiring path:

1. **luse-mcp-config.ts** sets `LUSE_REDIS_URL: process.env.REDIS_URL ?? ''` in the descriptor's `env` block (both per-WebApp variant and host variant).

2. **mcp/server.ts** at boot reads `process.env.LUSE_REDIS_URL`:
   - When present + non-empty → `new Redis(luseRedisUrl, {lazyConnect: true, maxRetriesPerRequest: 1})`. Lazy-connect means no socket is opened until the first `get`/`set` — keeps startup cheap.
   - When absent or empty → `redis = null`; the handler treats null as deny (fail-closed).

3. **`registerLuseTools(server, {streamManager, redis, userId, defaultDisplay})`** receives the fresh client.

The fresh-per-child pattern mirrors the existing per-process ioredis pattern in `capabilities.ts:596` (`_redis = new Redis(process.env.REDIS_URL || 'redis://localhost:6379', ...)`) — every module that talks Redis owns its own client.

## StreamManager target union

```typescript
// Before P100-10-04:
export type VncWindowTarget = {wid: number}

// After:
export type VncWindowTarget = {wid: number} | {display: string}
```

The `startStream({mode:'vnc-window', target, userId})` branch now:
1. Reads `'wid' in target` + `'display' in target` to determine the variant.
2. Validates exactly one is set (rejects both empty + mixed-non-empty).
3. Threads the appropriate value to `spawnVncForWindow({wid?, display?, rfbPort, ...})` — which has accepted both shapes since 100-10-01.
4. Stores both `wid?` and `display?` on the `VncSession` for crash logging + lifecycle teardown.

The idempotency cache key (`JSON.stringify(target)`) naturally separates the two variants: `'{"wid":2748}'` vs `'{"display":":10"}'` hash differently → two distinct sessions + ports.

### Rule 2 — `streamManager` field is duck-typed in mcp/tools.ts to avoid module cycle

**Found during:** Task 2 GREEN.

**Issue:** Direct `import {StreamManager} from '../../streaming/stream-manager.js'` into `computer-use/mcp/tools.ts` would create a cycle if streaming ever imported from computer-use (currently it doesn't, but Wave 5 UI plans may pull in either way). To keep computer-use module-graph independent, the streamManager field uses a minimal duck-typed interface (just `startStream(...)` + `listStreams(...)` signatures).

**Fix:** `LuseToolsOptions.streamManager?: {startStream(...); listStreams(...)}`. The real `StreamManager` class satisfies this contract at the wire-up call site. Tests pass plain object mocks.

**Disposition:** Not a bug — design choice for module isolation; ships forward unchanged.

### Note — Real cross-process StreamManager wire-up deferred

The MCP child process (spawned via `tsx mcp/server.ts`) cannot directly call the parent livinityd's `StreamManager` instance. This plan registers the stream tools ONLY in test mocks via direct injection; in the production MCP child, `streamManager` is undefined → the tools are NOT registered there → the agent sees the schemas via enumeration but the handlers aren't reachable.

A real cross-process bridge (HTTP/RPC to livinityd → StreamManager) is a separate plan — likely 100-10-05+ or v34. Current plan satisfies the locked acceptance criteria (which only require test-level wire-up + Redis flag check + display-target plumbing) without claiming production wire-up that doesn't exist.

This is consistent with the plan's `streamManager: StreamManager` signature in `LuseToolsOptions` and the test pattern. UAT row 8 (`mcp__luse__create_stream` callable from chat) will surface this gap during 100-10-07 walk; deferring the bridge work to a follow-up plan rather than overloading this wave's scope.
