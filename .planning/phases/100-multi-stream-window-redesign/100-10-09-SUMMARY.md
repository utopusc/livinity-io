# Phase 100-10-09 SUMMARY

**One-liner:** Fixed three MCP routing bugs surfaced by live UAT — Luse MCP child now targets DISPLAY=:1 by default (was :0, blinding AI to WebApp Chromes); boot-time idempotent migration sweeps legacy `liv:cap:mcp:bytebot` Redis key + stale `bytebot` McpConfigManager entry from the 100-10-02 source rename; UI MCP discovery now consistently surfaces "luse" instead of leaking the orphan "bytebot" name. ## Three Issues Fixed

### Issue 1 — Luse MCP child targeted :0 instead of :1 (AI blind to WebApp Chromes)

**Symptom (live UAT 2026-05-10):** Chrome WebApps spawn on Xvfb display `:1` (Phase 100-08-01 baseline, preserved through 100-10-08 revert) but `mcp__luse__list_windows` returned Bruce's host GNOME windows (Desktop Icons, Software Updater, crash notification) — NOT the WebApp Chromes. AI could not screenshot, focus, or interact with WebApp state.

**Root cause:** `buildLuseConfig` host variant used `DISPLAY: env.DISPLAY ?? ':0'`. systemd's livinityd unit env inherits `DISPLAY=:0` (host GNOME session legacy compat), so the spawned MCP child was routed to `:0` even though `:1` is where the Chromes live.

**Fix:** Changed host variant to `DISPLAY: env.LUSE_DISPLAY ?? ':1'`. The fall-through to `env.DISPLAY` is REMOVED entirely so systemd inheritance can no longer override the default. Legacy host-desktop-stream native app callers (rare) set `LUSE_DISPLAY=:0` explicitly if they need :0.

### Issue 2 — UI MCP panel shows "bytebot" even after 100-10-02 rename

**Symptom (live UAT 2026-05-10):** UI surfaces "bytebot" as MCP server name. Source files all use 'luse' since 100-10-02.

**Root cause:** 100-10-02 migrated source identifiers but NOT Redis-stored state. The cap-registry key `liv:cap:mcp:bytebot` (written before the rename) survived restarts. UI's MCP discovery reads `liv:cap:*` and picked up the orphan.

**Fix:** New `cleanupLegacyBytebotState` boot-time migration deletes `liv:cap:mcp:bytebot` (Step 1) + SCAN+DEL any orphan `liv:cap:tool:mcp_bytebot_*` tool entries (Step 2, defensive — capability-registry usually skips `mcp__` tools per `:180`, but historical state predating that filter is swept).

### Issue 3 — McpConfigManager has stale 'bytebot' server entry surviving rename

**Symptom:** McpConfigManager `listServers()` returns BOTH 'bytebot' (legacy) AND 'luse' (post-rename install) — `registerLuseMcpServer` installed fresh 'luse' alongside the existing 'bytebot' instead of replacing it.

**Root cause:** `registerLuseMcpServer`'s idempotency check filters by name=='luse' so it never sees the orphan 'bytebot' entry.

**Fix:** Cleanup Step 3 calls `mcpConfigManager.removeServer('bytebot')` if the entry exists (`listServers().some(s => s.name === 'bytebot')`). The real `McpConfigManager` (liv/packages/core/src/mcp-config-manager.ts:89) already exposes `removeServer(name): Promise<boolean>` — no new method needed in liv-core; the cleanup narrows on `typeof mcpConfigManager.removeServer === 'function'` for back-compat with test stubs that don't implement it.

## Changes

### `luse-mcp-config.ts`

- Host variant env: `DISPLAY: env.DISPLAY ?? ':0'` → `DISPLAY: env.LUSE_DISPLAY ?? ':1'`. Fall-through to `env.DISPLAY` removed (was the systemd-inheritance gap).
- `McpConfigManagerLike` extended with optional `removeServer?(name): Promise<boolean>`.
- Comments updated to attribute the change to Phase 100-10-09 with the UAT context.

### `legacy-bytebot-cleanup.ts` (NEW, 117 lines)

Exports `cleanupLegacyBytebotState({redis, mcpConfigManager, logger?})`. Three idempotent steps:
1. `redis.del('liv:cap:mcp:bytebot')` — sweep the cap-registry orphan.
2. `redis.scan` for `liv:cap:tool:mcp_bytebot_*` with chunked DEL (100 keys/cmd) — defensive sweep.
3. `mcpConfigManager.removeServer('bytebot')` if present — duck-typed via `typeof === 'function'` so test stubs without `removeServer` don't crash.

Each step is wrapped in its own try/catch. Errors collect onto `result.errors` but do NOT throw — boot must continue. Logger defaults to no-op (test path) or `livinityd.logger` (production wire).

### `agent-runs.ts` wire-up

The cleanup call is inserted in `mountAgentRunsRoutes`, AFTER `McpConfigManager` construction and BEFORE `registerLuseMcpServer`. Wrapped in `.catch()` for defense-in-depth (cleanup's internal try/catch should already swallow everything, but the outer .catch() ensures even unknown errors are non-fatal).
