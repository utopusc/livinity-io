# Phase 100-10-11 SUMMARY — Per-WebApp cascade window-position

**One-liner:** Replaced the hardcoded `--window-position=0,0` in `WebAppWindowManager.spawn()` with a 120px diagonal cascade computed from `this.active.size`. Two concurrent WebApps now spawn at (0,0) and (120,120) instead of stacking on the same origin. The 10-slot wrap with per-axis Y_RANGE=600 keeps every cascade slot strictly on-screen on the Xvfb :1 1920x1080 display. Sacred SHA `f3538e1d811992b782a9bb057d1b7f0a0189f95f` UNTOUCHED.

**Date:** 2026-05-10

## User UAT trigger

> "Pencereler Nedense gozukmuyor Ubuntuda ama iki tane pencere actigimda ust uste geliyor."
> ("Windows aren't visible in Ubuntu but when I open two windows they overlap.")

The Ubuntu-visibility piece is by-design (the user views WebApps via remote streams, not on the GNOME host display). The OVERLAP is the actual bug: every WebApp Chrome spawned with `--window-position=0,0`, so concurrent WebApps stacked on the same display origin and only the most-recently-raised window's pixels reached the x11vnc capture.

## Root cause

```ts
// pre-fix window-manager.ts:357
'--window-position=0,0',  // P100-06.1: predictable spawn coords ...
```

Predictable, yes. **Per-WebApp distinct**, no. The single-`:1`-display contract restored by 100-10-08 means all WebApp Chromes share one X display; they need distinct spawn positions to remain visually separable for x11vnc per-wid capture.

## Fix

`WebAppWindowManager.spawn()` now computes a cascade slot from the current map size BEFORE assembling the Chrome argv:

```ts
const CASCADE_PIXELS  = 120
const CASCADE_WRAP    = 10
const CASCADE_X_RANGE = 1200
const CASCADE_Y_RANGE = 600
const cascadeSlot     = this.active.size % CASCADE_WRAP
const cascadeOffsetX  = (cascadeSlot * CASCADE_PIXELS) % CASCADE_X_RANGE
const cascadeOffsetY  = (cascadeSlot * CASCADE_PIXELS) % CASCADE_Y_RANGE
const cascadeWindowPosition = `${cascadeOffsetX},${cascadeOffsetY}`
// ... later in argv:
`--window-position=${cascadeWindowPosition}`,
```

Per-slot positions for slots 0..9 (every slot is strictly on-screen):

| Slot | (x, y)     | Slot | (x, y)      |
|-----:|------------|-----:|-------------|
|    0 | (0,   0)   |    5 | (600, 0)    |
|    1 | (120, 120) |    6 | (720, 120)  |
|    2 | (240, 240) |    7 | (840, 240)  |
|    3 | (360, 360) |    8 | (960, 360)  |
|    4 | (480, 480) |    9 | (1080, 480) |

Slot 10 wraps back to (0, 0) — accepted degenerate case for 11+ concurrent WebApps per the plan's prose ("the 11th WebApp slot collides with #1").

## Plan deviation: Y_RANGE=600

The plan body's pseudocode for Task 2 used a flat `cascadeSlot * CASCADE_PIXELS` for BOTH X and Y. That formula sends slot 9 to y=1080, which equals the Xvfb :1 screen height — strictly off-screen for a 1280x720 Chrome window. T-10-11-CASCADE-02's `expect(y).toBeLessThan(1080)` assertion (written by the same plan body) would have failed.

I introduced `CASCADE_X_RANGE=1200` and `CASCADE_Y_RANGE=600` as per-axis modulos. This:

1. Preserves the plan's 10-slot wrap intent (slot 10 % 10 = 0, so 11th WebApp wraps to (0,0))
2. Keeps every cascade slot strictly on-screen (max y = 480 < 1080)
3. Produces 10 DISTINCT (x, y) pairs across slots 0..9 — each slot has a different x value, so even though y repeats every 5 slots, no two slots share the same (x, y).

The plan's earlier `<objective>` pseudocode actually used per-axis modulo (`(n*120) % 1200` and `(n*120) % 600`), so this aligns with the plan's stated intent — just deviates from the literal code in Task 2's `<action>` block.
