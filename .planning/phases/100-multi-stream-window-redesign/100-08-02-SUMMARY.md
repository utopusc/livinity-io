## XAUTHORITY non-leak verification (W1 fix)

The plan-checker's W1 concern: even though XAUTHORITY is no longer in WEBAPPS_X11_ENV, `env: {...process.env, ...WEBAPPS_X11_ENV}` still spreads `process.env` first, so any inherited `process.env.XAUTHORITY` may still flow into the spawned Chrome's environment. Resolution:

1. **Argv-prefix drop** — the user-visible `XAUTHORITY=...` line in `chromeArgs` (window-manager.ts) and `args` (vnc-bridge.ts) is REMOVED. This is the line that would have hard-coded `/run/user/1000/gdm/Xauthority` into the spawned child's effective environment via the `sudo VAR=val cmd ...` argv pattern. Without it, `sudo` no longer injects an XAUTHORITY env variable through the argv path.
2. **process.env.XAUTHORITY survival** — if the parent livinityd process happens to have `XAUTHORITY` set in its own env (e.g., from systemd unit file env_keep), the `{...process.env, ...WEBAPPS_X11_ENV}` spread MAY pass it to sudo's outer env. Sudo by default drops it (sudoers `env_reset`). On Mini PC's livinityd systemd unit (per CLAUDE.md memory) the unit env has only PATH/USER/HOME — XAUTHORITY isn't there to leak.
3. **Test 15 assertion** — the test sets `process.env.XAUTHORITY = '/should/not/leak'` then verifies `args.find(a => a.startsWith('XAUTHORITY='))` is `undefined`. Argv is the only path the parent can directly steer the child's X-auth — the test guards exactly that surface.
4. **Defense in depth** — Xvfb on `:1` is started with `-ac` (100-08-01 lifecycle): even if a stale XAUTHORITY pointer reached Chrome through some unforeseen channel, Xvfb wouldn't honor it for access control because access control is disabled.
