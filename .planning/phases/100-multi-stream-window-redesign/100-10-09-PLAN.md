# Plan 100-10-09: MCP DISPLAY routing + Redis legacy cleanup

<objective>
Live UAT on Mini PC 2026-05-10 surfaced three issues:

**Issue 1 — AI cannot see Chrome:**
- Chrome `--app=URL` spawns with `DISPLAY=:1` (correct, Phase 100-08-01 baseline + 100-10-08 revert)
- xvfb daemon runs on `:1` (correct)
- BUT the Luse MCP child process has `DISPLAY=:0` (Bruce's host GNOME desktop)
- → `mcp__luse__list_windows` returns Bruce's GNOME windows (Desktop Icons, Software Updater, crash notification) — NOT the Chrome WebApp windows that exist on `:1`
- → AI is blind to all WebApp Chrome state. Cannot screenshot, focus, or interact with them.

**Issue 2 — UI shows "bytebot" not "Luse":**
- 100-10-02 renamed source files + identifiers from bytebot to luse
- `buildLuseConfig` returns `name: 'luse'` (line 248)
- BUT Redis still has `liv:cap:mcp:bytebot` and 20+ `liv:cap:tool:mcp_bytebot_*` entries from pre-rename registrations
- UI's MCP discovery reads `liv:cap:*` namespace → shows the stale `bytebot` entry → user sees "bytebot" name even though source registers as "luse"

**Issue 3 — Stale McpConfigManager entry:**
- McpConfigManager.installServer for `luse` finds NO matching entry by name (existing is `bytebot`)
- → installs a new `luse` server alongside the old `bytebot` server
- → two MCP server registrations, UI shows the legacy one (alphabetical or by install-order)
- → fresh registration never takes effect for the UI

**Root cause of all three:** 100-10-02 rename migrated source code but did NOT migrate Redis-stored state. Mini PC restarted with new source but stale Redis state survived.

This plan ships:
1. `luse-mcp-config.ts`: host variant DISPLAY default `:1` (was `:0`). Override via `LUSE_DISPLAY` env still respected.
2. New `legacy-bytebot-cleanup.ts` module: boot-time idempotent migration that deletes stale Redis legacy entries + removes `bytebot` McpConfigManager server entry.
3. Wire-up in `livinityd/source/index.ts`: call cleanup BEFORE `registerLuseMcpServer` at boot.

After deploy:
- Luse MCP child process env: `DISPLAY=:1` (or whatever `LUSE_DISPLAY` says)
- Redis: zero `liv:cap:mcp:bytebot` and `liv:cap:tool:mcp_bytebot_*` entries
- McpConfigManager: only `luse` server (no orphan `bytebot`)
- UI MCP panel: shows "luse" as the MCP server name + 20 tools (`mcp__luse__*` + native tools)
- AI can `list_windows` and see Chrome WebApp windows on `:1`

  const store = new Map<string, string>();

    del: async (...keys: string[]) => { keys.forEach(k => store.delete(k)); return keys.length; },
    scan: async (cursor: string, ..._args: string[]) => {
      // simplified: returns all matching keys in one pass
      const match = _args.find((_, i) => _args[i-1] === 'MATCH');
      const keys = [...store.keys()].filter(k => match ? new RegExp(match.replace('*','.*')).test(k) : true);
      return ['0', keys];
    },
    set: async (k: string, v: string) => { store.set(k, v); return 'OK'; },
    __store: store,
  };

```ts
import type {Redis} from 'ioredis';
import type {McpConfigManagerLike} from './luse-mcp-config.js';

/**
 * Phase 100-10-09 — Idempotent cleanup of legacy bytebot Redis state +
 * stale McpConfigManager entry.
 *
 * Before 100-10-02 rename, the MCP server was registered as 'bytebot' in
 * McpConfigManager. The associated capability registry entries lived under
 * `liv:cap:mcp:bytebot` and `liv:cap:tool:mcp_bytebot_*` Redis keys. After
 * the rename, fresh installs register under 'luse' but the old state is
 * orphaned — UI MCP discovery still picks up the legacy 'bytebot' entries
 * causing user-visible confusion ("Bytebot" name in UI even after rename).
 *
 * This cleanup runs ONCE at livinityd boot, before registerLuseMcpServer,
 * and removes the orphans. Idempotent — safe to run on every boot.
 *
 * Failure mode: ANY error in cleanup is logged but does NOT throw. livinityd
 * boot continues regardless — cleanup is a best-effort hygiene step.
 */

export interface CleanupOpts {
  redis: Pick<Redis, 'del' | 'scan'>;
  mcpConfigManager: McpConfigManagerLike;
  logger?: {log(msg: string, ...args: unknown[]): void; error(msg: string, ...args: unknown[]): void};
}

export interface CleanupResult {
  redisKeysDeleted: number;
  mcpServersRemoved: number;
  errors: string[];
}

export async function cleanupLegacyBytebotState(
  opts: CleanupOpts,
): Promise<CleanupResult> {
  const {redis, mcpConfigManager} = opts;
  const log = opts.logger ?? {log: () => {}, error: () => {}};
  const result: CleanupResult = {redisKeysDeleted: 0, mcpServersRemoved: 0, errors: []};

  // Step 1 — Delete the bare cap:mcp:bytebot key
  try {
    const n = await redis.del('liv:cap:mcp:bytebot');
    result.redisKeysDeleted += n;
  } catch (err) {
    const msg = `del liv:cap:mcp:bytebot failed: ${(err as Error).message}`;
    log.error(`[100-10-09 cleanup] ${msg}`);
    result.errors.push(msg);
  }

  // Step 2 — SCAN+DEL the tool entries (avoid blocking KEYS)
  try {
    let cursor = '0';
    const batch: string[] = [];
    do {
      const reply = (await redis.scan(
        cursor,
        'MATCH',
        'liv:cap:tool:mcp_bytebot_*',
        'COUNT',
        '200',
      )) as [string, string[]];
      cursor = reply[0];
      batch.push(...reply[1]);
    } while (cursor !== '0');
    if (batch.length > 0) {
      // Delete in chunks of 100 to avoid command-too-large
      for (let i = 0; i < batch.length; i += 100) {
        const slice = batch.slice(i, i + 100);
        const n = await redis.del(...slice);
        result.redisKeysDeleted += n;
      }
    }
  } catch (err) {
    const msg = `scan/del liv:cap:tool:mcp_bytebot_* failed: ${(err as Error).message}`;
    log.error(`[100-10-09 cleanup] ${msg}`);
    result.errors.push(msg);
  }

  // Step 3 — Remove the stale McpConfigManager 'bytebot' server entry
  try {
    const servers = await mcpConfigManager.listServers();
    const hasBytebot = servers.some((s) => s.name === 'bytebot');
    if (hasBytebot && 'removeServer' in mcpConfigManager) {
      const removed = await (mcpConfigManager as any).removeServer('bytebot');
      if (removed) result.mcpServersRemoved += 1;
    }
  } catch (err) {
    const msg = `mcpConfigManager.removeServer('bytebot') failed: ${(err as Error).message}`;
    log.error(`[100-10-09 cleanup] ${msg}`);
    result.errors.push(msg);
  }

  log.log(
    `[100-10-09 cleanup] complete — redisKeysDeleted=${result.redisKeysDeleted} mcpServersRemoved=${result.mcpServersRemoved} errors=${result.errors.length}`,
  );

  return result;
}
```
