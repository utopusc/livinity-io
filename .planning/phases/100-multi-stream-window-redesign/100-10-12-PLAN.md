Reference: https://github.com/utopusc/selfclaude — user's hackathon project that demonstrates the desired Teach pattern.

Today's LivOS Teach mode (P95-P96 + 100-09 hot-fixes):
- Click record button → starts continuous screenshot capture loop (`setInterval` or similar) at ~1 fps
- Captures every event as a timestamped frame
- Replay = replay-from-log (timeline-based)

Desired SelfClaude pattern (per user):
- Click record button → tool armed, NO continuous capture loop
- User CLICKS something on the stream → that single click registers as a discrete "step"
- After each click step, user prompts an instruction (text) that describes WHAT this step is for
- Build up an instruction-annotated action sequence: `[click @(x,y)] "open Gmail" / [click @(x,y)] "click compose" / ...`
- Replay = re-execute the action sequence (no timeline; each step has explicit semantics)

This is the difference between FRAME-BASED capture (timeline) and EVENT-BASED capture (semantic). The user wants semantic. This is the SelfClaude philosophy: each click is a teachable moment with explicit annotation.

**Why this research-only plan instead of immediate implementation:**

1. The current click-routing infrastructure (P100-07, action_log v2 with `mcp__bytebot__click_mouse` → `mcp__luse__click_mouse` after 100-10-02) is INTERVAL-DRIVEN. Refactoring to event-driven requires deep changes to:
   - WebApp window event capture pipeline (xdotool key-monitor → action-tagged emit)
   - Action storage format (action_log v2 → v3: add `instruction: string` per event)
   - Replay engine (frame-perfect timing → event-sequential, instruction-acknowledged)
   - UI: between-step prompt input (modal? floating box anchored to click point?)
   - Backwards-compat: old v2 logs replay via lazy-translation shim (already in place); new v3 records future steps

2. The capture path on Linux/X11 needs robust click detection. Today's path uses xdotool-spy patterns; SelfClaude likely uses CDP (`Page.handleClickEvent` or `Input.dispatchMouseEvent` callbacks). Phase 101 plans CDP orchestration — the right host for this work.

3. User confirmed Phase 101 vision (2026-05-10 UAT): "Luse kendi kendine port acip o portda uygulamalar calistirabilir mi full screen de? Bu portlarinda ayni Resulutionu olmali. YTani tek bir mcp ve bir suru screen tool u istiyorum." This is the CDP-driven Luse orchestration vision. SelfClaude Teach pattern fits naturally inside that architecture (CDP gives clean per-click events).

## What the user wants

Teach mode should be EVENT-DRIVEN, not interval-driven:

1. User clicks "Record" / "Teach" button → mode enters armed state. NO continuous capture starts.
2. User CLICKS on the WebApp stream (a single click on a real UI element).
3. The system PAUSES, opens a small "What was that for?" prompt anchored near the click point.
4. User types an instruction in plain language: e.g. "Click the search box".
5. User submits → step is recorded as `{action: 'click', x: 543, y: 287, instruction: "Click the search box", timestamp: T}`.
6. Mode returns to armed; user can click again to record next step.
7. User clicks "Stop" / "Save" to finalize the skill.

Replay:
- For each step, executor runs the action (e.g. xdotool click @x,y on the WebApp's wid OR the Luse agent reads the instruction and performs the click via screenshot+click chain).
- The instruction is the HINT for the agent during replay — if pixel coords drift (window resized, UI changed), the agent uses the instruction text as a high-level recovery prompt.

## Current LivOS Teach (P95-P96 + 100-09 baseline)

- INTERVAL-DRIVEN: timer fires every ~1s, captures a frame
- Frames have timestamps; replay = re-emit frames at recorded timing
- No semantic annotation; debugging a flaky replay means reading raw mouse coordinates

This is the wrong abstraction for the user's use case.

## Data model diff

### v2 (today)

```json
{
  "version": 2,
  "events": [
    {"t": 1717000000000, "type": "frame", "screenshot": "<base64>"},
    {"t": 1717000001000, "type": "click", "x": 543, "y": 287, "wid": "0x..."}
  ]
}
```

### v3 (proposed SelfClaude pattern)

```json
{
  "version": 3,
  "steps": [
    {
      "t": 1717000000000,
      "action": {"type": "click", "x": 543, "y": 287, "wid": "0x...", "button": 1},
      "instruction": "Click the search box",
      "screenshot_before": "<base64>",
      "screenshot_after": "<base64>"
    },
    {
      "t": 1717000005000,
      "action": {"type": "type_text", "text": "hello world"},
      "instruction": "Type the search query",
      "screenshot_before": "<base64>",
      "screenshot_after": "<base64>"
    }
  ]
}
```

Backwards-compat: existing `mcp__bytebot__*` → `mcp__luse__*` shim (100-10-02 D-100-10-I) already routes v2 events. v3 introduces `steps` field; v2 `events` field still recognized by replay engine.

## UX flow

(see attached wireframe-as-ascii in Phase 101 design phase)

1. WebApp stream visible. Teach button in floating bottom bar (post-100-10-05 outside-window pattern).
2. Click Teach → button turns red (already done in 100-09-09), small "Click to record step" caption shows.
3. User clicks anywhere in the stream area → click is captured, stream is BRIEFLY paused, a popover anchored to click point: "What did you do?" with text input + Save button.
4. User types instruction + Save → step saved, popover closes, mode returns to armed-record.
5. Click Stop / Save → skill finalized with metadata (name? optional. Or auto-generate from first instruction).

## CDP vs xdotool capture comparison

| Aspect | xdotool spy (today) | CDP (Phase 101) |
|--------|---------------------|-----------------|
| Click event source | poll `xdotool getmouselocation` (laggy, missed events) | `Input.dispatchMouseEvent` callback (frame-perfect) |
| Modifier capture | requires xinput tracking | CDP carries modifier flags |
| Cross-window | manual wid wrangling | CDP scopes to target |
| Replay precision | timing drift | CDP can re-dispatch with original modifier flags |
| Privacy/scope | system-wide (sees host clicks too) | scoped to Chrome target |

CDP wins for SelfClaude pattern. Aligned with Phase 101 overall direction.
