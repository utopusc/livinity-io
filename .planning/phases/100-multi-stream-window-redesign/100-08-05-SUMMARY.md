# Phase 100-08-05 SUMMARY

**One-liner:** Wire `webappId` end-to-end (UI useWebAppAgent → useAgentSocket WS envelope → livinityd broker `/api/agent/stream` body → liv api.ts `filterAdditionalMcpServers`) so a chat panel docked to WebApp A only sees A's `bytebot:webapp:<id>` MCP tools — with a graceful host-bytebot fallback during liv-core's ~1-2s Redis pub-sub reconcile lag.

**Date:** 2026-05-09
**Goal:** Land V33-08-05-WEBAPP-TOOL-SCOPE + V33-08-05-HOST-FALLBACK + V33-08-05-LAG-FALLBACK. Close the multi-stream tool-routing concern documented in CONTINUE.md without touching the sacred `sdk-agent-runner.ts`.

## Architectural revision (2026-05-09)

The original plan referenced `liv/packages/core/src/api.test.ts` which does NOT exist (verified via `test -f` pre-flight: `MISSING`). Tests now live in a NEW dedicated file `liv/packages/core/src/api.scope-filter.test.ts` mirroring the `mcp-client-manager.webapp-cap.test.ts` pattern (standalone tsx, `node:assert/strict`, no vitest).

In light of the Redis pub-sub reconciliation lag documented in 100-08-04-SUMMARY.md ("Risk model — Redis reconciliation lag", ~1-2s between livinityd's mcpConfigManager.installServer write and liv-core's McpClientManager.reconcile pickup), the scope filter is BEST-EFFORT: when the request's webappId is set BUT `bytebot:webapp:<webappId>` is not yet visible in `mcpConfigManager.listServers()`, the filter falls THROUGH to the host scope (host bytebot + user-installed MCPs visible) and logs a WARN with `{webappScope: <id>, fallback: 'lag'}`. The next chat turn (post-reconcile) gets the per-WebApp child as intended. This avoids the failure mode where users open a WebApp, type into its chat within ~1s, and see "no tools available."

## Architecture

### End-to-end webappId flow

```
<WebAppChatDrawer webappId="abc-uuid">
       ↓ prop
useWebAppAgent("abc-uuid")
       ↓ useAgentSocket({webappId: "abc-uuid"})
useAgentSocket → sendMessage builds payload = {type: 'start', prompt, webappId: "abc-uuid", ...}
       ↓ WS frame
livinityd ws-gateway → broker proxy → createSdkAgentRunnerForUser({..., webappId: "abc-uuid"})
       ↓ HTTP fetch
POST liv :3200 /api/agent/stream  body = {task, max_turns, conversationId, webappId: "abc-uuid"}
       ↓ body destructure
reqWebappId = "abc-uuid"
       ↓ filterAdditionalMcpServers(enabled, "abc-uuid", logger)
                                    ↓
                     ┌──────────────┴──────────────┐
                     │                             │
        bytebot:webapp:abc-uuid       bytebot:webapp:abc-uuid
        IS in listServers()           NOT in listServers()
                ↓                              ↓
        scope='webapp'                scope='lag-fallback'
        servers=[that one]            logger.warn({webappScope, fallback: 'lag'})
                                      servers=[host bytebot, user MCPs]
                                      (per-WebApp instances filtered out)
                ↓                              ↓
        agent only sees             agent sees host bytebot
        WebApp A's tools            (host scope tools, same as v32)
                                    Next turn (post-reconcile): scope='webapp'
```

### 3-state scope contract

```typescript
filterAdditionalMcpServers(enabledServers, reqWebappId, logger)
  → {scope: 'webapp' | 'host' | 'lag-fallback', servers: T[]}
```

| Input | Scope | Output servers | Side effect |
|---|---|---|---|
| webappId='abc' AND `bytebot:webapp:abc` ∈ enabled | `webapp` | `[bytebot:webapp:abc]` only | none |
| webappId='abc' AND `bytebot:webapp:abc` ∉ enabled | `lag-fallback` | host bytebot + user MCPs (NOT per-WebApp instances) | logger.warn({webappScope: 'abc', fallback: 'lag'}) |
| webappId=null (host home) | `host` | host bytebot + user MCPs (NOT per-WebApp instances) | none |

### Host home backward compat

Existing `useAgentSocket()` call sites (host home chat in v32) pass no opts → default `{}` → `opts.webappId === undefined` → no `webappId` in WS envelope → livinityd broker no `webappId` in body → reqWebappId=null → scope='host' → host bytebot + user MCPs as before. **Zero regression** on the v32 chat home.

## Risk model

| Risk | Mitigation |
|---|---|
| Liv-core reconcile lag → user types in WebApp chat before `bytebot:webapp:<id>` registered | Lag-fallback returns host bytebot scope + WARN log; user chat works (host scope tools) instead of failing with empty tools[]. Next turn gets per-WebApp child. T2 test enforces. |
| webappId points to a stale (closed) WebApp | Same lag-fallback path — listServers won't include the removed entry; falls through to host scope. WARN logged. |
| webappId injection from malicious UI | Single-user model (D-V33-07) makes this non-issue; user can only "spoof" their own WebApp scopes. Multi-user gating (verify webappId belongs to current user) deferred to v34. |
| Cross-scope tool leak (webappId='abc' returns 'bytebot:webapp:xyz') | Even on lag-fallback, the prefix-based filter `s.name.startsWith('bytebot:webapp:')` excludes ALL per-WebApp instances — a request for 'abc' never sees 'xyz' even if xyz is the only registered child. **T4 test enforces.** |
| Empty tools[] surprise | Eliminated by design — lag-fallback ALWAYS returns at least host bytebot. The only "empty" state is when liv-core has zero servers configured (which is a separate ops issue, not a 100-08-05 concern). |
