# Phase 100-10-10: WebApp chat-response wire-up + per-tool streaming UI Summary

User UAT 2026-05-10 reported two bugs on the floating action bar chat surface. Both shipped. Sacred SHA `f3538e1d811992b782a9bb057d1b7f0a0189f95f` UNTOUCHED.

## Bug A — Chat reply doesn't render in ChatResponseBar (FIXED)

**Root cause:** Hypothesis 2 from the plan confirmed. `useWebAppAgent(webappId)` was called twice — once in `ChatInputBar`, once in `ChatResponseBar`. Each call internally invokes `useAgentSocket({webappId})`, which is a per-hook-instance hook: it creates its own `wsRef` WebSocket and its own `useReducer` messages state. Two call sites = two WebSockets + two messages arrays.

When the user clicked Send, `handleSend` called `agent.sendMessage('hello')` on ChatInputBar's WS#A, then the parent flipped mode `chat-input → chat-response`. React's conditional JSX UNMOUNTED ChatInputBar — running its useEffect cleanup which set `intentionalCloseRef.current = true` and closed WS#A — BEFORE the assistant chunks arrived from the server. ChatResponseBar then MOUNTED, opening WS#B with an empty messages array. The streaming reply that the server was sending to the closed WS#A was lost; ChatResponseBar saw an empty `messages` array forever.

**Fix:** Hoist `useWebAppAgent(webappId)` to the parent `WebAppFloatingActionBar` (line 129). Pass `agent` as a prop into both `ChatInputBar` and `ChatResponseBar` via new interface fields `agent: UseWebAppAgentResult`. Single WebSocket persists across the mode flip; both sub-components observe the same messages + isStreaming + agentStatus state via reference identity.

## Bug B — Per-tool streaming status line (SHIPPED with graceful fallback)

**Backend gap discovered:** Phase 87 V32-HERMES `status_detail` chunks `{phase, phrase, elapsed}` are emitted by `liv-agent-runner.ts` (lines 611, 672, 751). BUT the chat WebSocket relay uses `agent-session.ts` (`AgentSessionManager` → Claude SDK `query()` direct relay) which does NOT forward runStore status_detail chunks. So `phrase` is null on the chat WS surface today.

**Existing signal that DOES work:** `use-agent-socket.ts` handles `stream_event/content_block_start` for tool_use blocks (line 230) by writing `setAgentStatus({phase: 'executing', currentTool: <tool_name>})`. So `currentTool` is correctly populated whenever a tool is being dispatched.

**Implementation:** Extended `AgentStatus` type with optional `phrase?: string | null` field (forward-compat). UI renders a status sub-line in BOTH `ChatResponseBar` (beneath the response text + caret) AND `ChatInputBar` (beneath the input pill, via a new `inline-flex flex-col` wrapper). Render shape:

```tsx
{agent.isStreaming && (agent.agentStatus?.phrase || agent.agentStatus?.currentTool) ? (
  <div className='text-caption-xs text-text-tertiary mt-1.5 flex items-center gap-1.5'>
    <span className='inline-block w-1 h-1 rounded-full bg-text-tertiary animate-pulse' aria-hidden='true' />
    <span>{agent.agentStatus.phrase ?? `Using ${agent.agentStatus.currentTool}…`}</span>
  </div>
) : null}
```

**What the user sees today:** When the agent dispatches a tool, the status line shows e.g. `● Using list_windows…`. Between turns (phase='thinking' with currentTool=null) the line hides — graceful empty state. When a future plan wires `agent-session.ts` to relay runStore `status_detail` chunks, the `phrase` field will populate and the line will show Hermes phrases like "Analyzing…" / "Reading file…" automatically with zero UI changes.
