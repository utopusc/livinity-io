**One-liner:** Reverted D-100-10-A (per-WebApp Xvfb) because Chrome singleton lock per `--user-data-dir` is architecturally incompatible with per-WebApp displays. ## Root cause (validated on Mini PC during 100-10-01 deploy)

Chrome enforces a singleton lock keyed on `--user-data-dir`. Behavior:

1. WebApp A spawns `google-chrome --user-data-dir=/home/bruce/.config/livos-chrome --app=URL_A` with `DISPLAY=:10`. Chrome bootstraps fresh on `:10`. Window appears. `xdotool search --name <hostname>` matches. ✓
2. WebApp B spawns the same Chrome binary with `DISPLAY=:11` + `--app=URL_B`. Chrome's IPC mechanism detects an existing PID owning the same `--user-data-dir`. The new process serializes its argv (`--app=URL_B`) to the existing PID and exits. The existing Chrome opens a new window for `URL_B` — but on `:10`, NOT `:11`.
3. `findNewWindowMatching` polls `xdotool search` against `:11` (`DISPLAY=:11` env). No window matching `URL_B` ever appears there. Timeout → `WindowNotFoundError: no new window matching URL_B appeared within timeout`.

Two ways out:
- (a) Drop the shared profile — give each WebApp its own `--user-data-dir`. Loses Google login + cookie continuity across WebApps. **Rejected by user.**
- (b) Revert per-WebApp displays — share a single display, let Chrome multi-window naturally on it, capture per-wid (Phase 99 baseline). **Chosen by user.**
