# Phase 100-09-02 SUMMARY

**One-liner:** Close 100-09 Bug 2 (scroll-down doesn't work) by adding the missing wheel listener (user-canvas tRPC path) and routing bytebot `computer_scroll` through the activate-first xdotool chain (button 4/5/6/7). Same Chrome XSendEvent filter pattern as 100-07.3 click fix.

**Date completed:** 2026-05-09
**Sacred SHA gate:** PASSED (byte-identical pre + post all commits).

## Goal

After this plan ships:
1. User can scroll down with the mouse wheel inside any WebApp stream window — page scrolls down (was previously no-op because the noVNC canvas is `viewOnly: true` per 100-07 and no `wheel` listener routed events through tRPC).
2. Bytebot `computer_scroll {direction: 'down', scrollCount: 3}` actually scrolls down inside the bound WebApp's Chrome (was previously dropped by Chrome's synthetic-event filter against nut-js's XTestFakeButtonEvent).

## Root cause analysis

### User-canvas path (tRPC)
- `webapp-stream-window.tsx` `useEffect` block (lines 190-333) attached `mousedown`, `mouseup`, `contextmenu`, `keydown` listeners but NO `wheel` listener.
- `viewOnly: true` (P100-07) on the noVNC RFB transport means scroll events from the user's wheel never reach the captured Chrome via x11vnc either.
- The tRPC router had no `webapp.input.scroll` mutation (only `click`, `keypress`, `type` — see `inputRouter` at trpc-router.ts:209).
- Result: scroll wheel was a complete no-op for users.

### Bytebot path (computer_scroll tool)
- `native/input.ts:scroll` used nut-js `mouse.scrollDown(n)` which dispatches synthetic XTestFakeButtonEvent.
- Chrome's XSendEvent filter (the same one that broke `xdotool click --window` pre-100-07.3) silently drops these synthetic button events.
- `mcp/tools.ts:computer_scroll` did NOT thread the resolved wid into the scroll opts (despite the plan's note saying it did — code read showed otherwise; this was a Rule 3 fix).
- Result: bytebot agent's scroll tool fired but nothing happened in the captured Chrome.
