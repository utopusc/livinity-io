## Schema migration note (action_log v2)

**No SQL migration required.** `webapp_skills.action_log` is a JSONB column. The Postgres column accepts arbitrary shape; the change is purely the zod validator on the create path. Existing v1 rows in production remain valid (the discriminated union admits both `version: 1` and `version: 2` literals). New recordings emit v2; reads return whatever shape was stored at write time.

**Lazy upgrade pattern.** Since the daemon-side schema accepts both literals, existing v1 logs from the P96 era continue to validate on load. The replay path can branch on `log.version === 2` to render new affordances (inline thumbs from `screenshot_b64`, viewport-aware coordinate scaling), and falls back to v1 behavior when the field is absent. No backfill required.

**v3+ records are rejected.** Test T-09-06-S3 asserts that a `{version: 3}` record fails zod validation, so future shape changes will require an explicit schema bump and a new test (rather than silently accepting unknown shapes).

## Deviations from Plan

Three minor deltas — all documented inline; all kept under Rule 1/2 auto-fix scope:

1. **[Rule 3 - Blocking] WebAppMode import preservation.** The plan suggested dropping `WebAppMode` import + the `mode`/`setMode` local state since the recorder is now Zustand-driven. The pre-existing source-text invariant `useState<WebAppMode>('chat')` (line 36 of webapp-stream-window.unit.test.tsx) would have failed on full removal. Compromise: kept the `useState<WebAppMode>('chat')` declaration with an eslint-disable comment + a Phase 100-09-06 explanatory comment block (line 393-399 of webapp-stream-window.tsx); the state hook is a no-op now (no reader). This preserves the invariant lock without contributing to runtime behavior.

2. **[Rule 1 - Bug] Skills popover field name.** The plan's <interfaces> sketch used `{s.name}` for the row label, but the actual `webapp.skills.list` response shape is `{id, skillName, createdAt, actionCount}` (per skills-router.test.ts T4). The component was written with the correct field name `s.skillName`.

3. **[Rule 1 - Bug] onStopRecording route through drawer store.** The plan kept the existing imperative `recorder.stop()` call inside `onStopRecording` (used by the TeachRecordingOverlay's Stop button), creating two parallel stop pipelines (one driven by drawer-store flip, one direct). To prevent races between them, `onStopRecording` was rewired to call `toggleTeachRecording(webappId)` — single source of truth for the recorder lifecycle. The existing useEffect then handles the actual stop + Save dialog open.
