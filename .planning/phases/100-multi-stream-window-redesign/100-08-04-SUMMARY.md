## Architectural revision (2026-05-09)

The original plan (pre-revision) called `this.ai.mcpClientManager.registerWebAppInstance(...)` directly. **That was wrong:** McpClientManager lives in liv-core (port 3200), a SEPARATE process from livinityd. The canonical pattern, documented inline in `livos/packages/livinityd/source/modules/ai/agent-runs.ts:52-58, 161-164`, is:

> livinityd writes to Redis via its own McpConfigManager → liv-core's McpClientManager subscribes to `liv:config:updated` → reconciles asynchronously (~1-2s lag).

This plan implements that pattern. Sentinel grep confirms zero references to `mcpClientManager.registerWebAppInstance` / `deregisterWebAppInstance` / `mcpClientManager` in production code (window-manager.ts, source/index.ts) — verified post-commit.

## Architecture

### Server name format

`bytebot:webapp:<webappId>` — matches `McpClientManager.WEBAPP_INSTANCE_NAME_PREFIX` so liv-core's reconcile path treats these as per-WebApp bytebot children (not generic MCP servers). The prefix is the routing pivot for the 08-05 chat-surface scope filter.

### Cross-process bridge (Redis pub-sub)

```
livinityd (port 8080)              liv-core (port 3200)
─────────────────────              ─────────────────────
window-manager.spawn()
  └─> registerWebAppMcp()
       └─> mcpConfigManager
              .installServer({         McpClientManager
                name: bytebot:        ─── async ~1-2s ───>  .reconcile()
                webapp:<id>, ...})        Redis pub-sub          ↓
              ↓                       liv:config:updated     spawn child
         saveAndPublish()                                    `bytebot:webapp:<id>`
              ↓                                              with BYTEBOT_TARGET_WINDOW_ID
        Redis SET liv:mcp:config                             + DISPLAY=:1 in env
        Redis PUBLISH liv:config:updated 'mcp_config'
```

Same shape on close, with `removeServer` instead of `installServer`.

### Idempotency / regex fallback

`McpConfigManager.installServer` enforces a name regex `/^[a-z0-9][a-z0-9_-]*$/` (line 57 of `liv/packages/core/src/mcp-config-manager.ts`) which **rejects names containing colons** like `bytebot:webapp:abc`. P97-06's webapp-cap test (`mcp-client-manager.webapp-cap.test.ts`) bypasses this via FakeConfigManager — production behavior may not have hit the regex limitation in the wild yet.

`registerWebAppMcp` handles this pragmatically:
1. Try `installServer(config)` first.
2. On any throw (regex rejection OR duplicate-name from re-spawn), fall back to `updateServer(name, config)` which has no regex.
3. If `updateServer` returns null (entry doesn't exist AND installServer refused), re-throw the original install error so the outer catch logs it.

This means: even if the regex blocks first install, AND the entry doesn't yet exist (so updateServer returns null), the error is logged WARN and spawn() returns successfully — the host bytebot fallback (broadcastActiveWid IPC) carries the agent.

### Belt-and-braces fallback

`/tmp/livos-active-webapp-wid` (P100-07.4 file IPC) **REMAINS** in spawn/close. Two reasons:
1. **Reconcile lag bridge** — during the ~1-2s window between livinityd's Redis publish and liv-core picking up the change, host bytebot via the file IPC still routes to the most recently active WebApp.
2. **Legacy host bytebot** — the host-display bytebot child (registered by `agent-runs.ts:179`) serves the `desktop-stream` native app and any other non-WebApp surfaces. Its scoping continues to use the file IPC for the single-active-WebApp case.

## Risk model — Redis reconciliation lag

| Risk | Mitigation |
|---|---|
| Chat fires before liv-core reconciles new per-WebApp child | 08-05 scope filter falls through to host bytebot for that turn (best-effort, logged WARN). Documented in carryover. |
| Chat fires after WebApp closed but before liv-core processes removeServer | Same — host bytebot fallback. Stale per-WebApp child eventually cleaned up by reconcile. |
| `installServer` regex `/^[a-z0-9][a-z0-9_-]*$/` rejects `bytebot:webapp:abc` (colons) | `registerWebAppMcp` catches the throw, falls back to `updateServer` (no regex). Tests Test 18 + Test 19 cover both the success-via-fallback and total-failure-non-fatal cases. |
| Spawn() rejected because MCP registration threw | NOT POSSIBLE — registerWebAppMcp's outer catch returns void. Test 19 explicitly asserts `mgr.spawn(...)` resolves with a valid SpawnResult even when both installServer AND updateServer fail. |

## Known issue (out of scope; flag for v34)

The `installServer` regex in `liv/packages/core/src/mcp-config-manager.ts:57` (`/^[a-z0-9][a-z0-9_-]*$/`) does not allow colons in server names, but `bytebot:webapp:<id>` contains colons. The `registerWebAppMcp` helper handles this via `updateServer` fallback, but P97-06's webapp-cap test bypasses production code via FakeConfigManager — the regex limitation may not have been hit in real production yet.

**v34 cleanup:** relax the regex in `mcp-config-manager.ts:57` to allow the `bytebot:webapp:` prefix (e.g., `/^[a-z0-9][a-z0-9_:-]*$/` or a more targeted prefix-allowlist). Then `installServer` would succeed on first call and the fallback path becomes a pure idempotency safety net for re-spawn.
