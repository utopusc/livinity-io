# Plan 100-10-08: Revert per-WebApp Xvfb (D-100-10-A revert)

<objective>
After 100-10-01 ship + Mini PC deploy, multi-stream WebApp window spawn fails with `WindowNotFoundError: no new window matching <url> appeared within timeout`. Live diagnostic on Mini PC confirmed the root cause:

- Chrome `--user-data-dir=/home/bruce/.config/livos-chrome` (D-100-SHARED-PROFILE) → enforces a singleton lock per user-data-dir
- New WebApp spawn with `DISPLAY=:11, --app=URL` → Chrome's IPC redirects to the existing PID on `:10` → no window appears on `:11` → discovery timeout

D-100-10-A (per-WebApp Xvfb display `:10`, `:11`, ...) is **architecturally incompatible** with D-100-SHARED-PROFILE. Either drop the shared profile (losing same-Google-login multi-stream) or revert per-WebApp displays.

User has chosen to keep shared profile + same Google login. This plan reverts D-100-10-A back to Phase 99 single-display behavior:

- All WebApp Chromes spawn on a single shared Xvfb display (`:1`)
- Chrome singleton naturally allows multi-window on the same display (one process, multiple `--app=URL` windows)
- `x11vnc -id <wid>` per-WebApp captures each window independently (Phase 99 path)
- Per-WebApp `LUSE_DISPLAY` env defaults to `:1` (single display)
- DisplayAllocator code stays in tree but is unused (kept as scaffold for Phase 101 CDP architecture)

Preserves all other 100-10 work:
- 100-10-02 Bytebot→Luse rename ✓ kept
- 100-10-03 Luse window tools (list_windows, screenshot_window, focus_window) ✓ kept (operate on `:1`)
- 100-10-04 Luse stream tools (create_stream, list_streams) ✓ kept (default display `:1`)
- 100-10-05 UI cleanup (skill button outside, full-fit, remove Auto) ✓ kept
- 100-10-06 chat-response 3-mode ✓ kept

Sacred SHA `f3538e1d811992b782a9bb057d1b7f0a0189f95f` MUST stay unchanged.
</objective>

<must_haves>
- `WebAppWindowManager.spawn` allocates per-WebApp WID on single shared `:1` display (no Xvfb spawn per WebApp)
- DisplayAllocator file stays but `spawn()` does NOT call `allocateNextXvfbDisplay()` — instead constant `:1`
- `vnc-bridge.ts` defaults to `-id <wid>` mode (Phase 99 / 100-08 behavior); `-display :N` branch stays in code for Phase 101 CDP path but is not exercised here
- `LUSE_DISPLAY` env defaults to `:1` for all per-WebApp MCP children
- Two concurrent WebApps spawn successfully (Chrome singleton allows multi-window on same display)
- Each WebApp has its own wid, x11vnc captures each wid independently
- Same Chrome profile shared (Google login works across WebApps)
- Sacred SHA preserved across all commits
- Tests pass: window-manager + vnc-bridge + display-allocator
