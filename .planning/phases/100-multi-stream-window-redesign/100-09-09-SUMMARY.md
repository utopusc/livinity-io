# Phase 100 Plan 09-09: Teach Button Red + Click Count Badge Summary

**One-liner:** Rewires the Teach-mode recording UX per user feedback after the 09-06 deploy. The top-right `TeachRecordingOverlay` widget (pulse-red dot + "Recording · N events" text + separate Stop button) is REMOVED. The Teach icon button in the floating action bar (outside the WebApp window per 100-06) now turns red (`bg-red-500/90`) while `isRecording` is true and renders a small numeric badge with the live click count (`events.length` from the recorder) at the top-right corner of the button. Clicking the now-red button stops recording — reusing the existing 09-06 `toggleTeachRecording` → useEffect → `recorder.stop()` → `SaveSkillDialog` pipeline. Sacred SHA `f3538e1d811992b782a9bb057d1b7f0a0189f95f` preserved across both commits.

## What user reported

Verbatim feedback after the 09-06 deploy:

> "Suan teach e tikliyorum geri tikladigimda duruyor bu guzel ama tikladiktan sonra kirmizi buton olsun teach. sag yukarida stop butonu olmasin ve sure saymasin sadece clickleri saysin."

Translation: "Right now I click teach, click again it stops — that's good. But after clicking, the teach button should be red. No stop button at top-right, no time counter, only count clicks."

## What 09-06 shipped wrong

09-06 introduced `TeachRecordingOverlay` — a top-right widget anchored at `absolute right-3 top-3` over the WebApp stream window:

```
┌──────────────────────────────────────┐
│                          ┌─────────┐ │
│   [Gmail stream]         │ • REC   │ │ ← TeachRecordingOverlay
│                          │ N evts  │ │   (pulse-red dot, event
│                          │ [Stop]  │ │    counter, separate Stop)
│                          └─────────┘ │
│   [💬] [🎓] [🤖]                     │ ← floating bar (Teach icon
└──────────────────────────────────────┘   stayed visually neutral)
```

The Teach icon in the floating action bar that STARTED the recording stayed visually neutral (no red, no count). The "Stop" affordance was a separate button inside the top-right overlay. The overlay text included `eventCount` (which IS the click count) AND `droppedCount` (which can read like time/event noise to users).

Per user feedback, this split-surface design was confusing: the same action ("am I currently recording? if so, stop it.") was scattered between two visually disconnected widgets. The fix: collapse start + stop + count onto the single Teach icon button.

## What 09-09 ships

**Single-surface Teach-button state machine.** The Teach icon in the floating action bar (rendered OUTSIDE the WebApp window per 100-06) becomes red while recording AND shows a live click-count badge:

```
mode='icons', NOT recording:    mode='icons', RECORDING (3 clicks captured):
┌──────┐ ┌──────┐ ┌──────┐      ┌──────┐ ┌───────┐ ┌──────┐
│ Chat │ │Teach │ │ Auto │      │ Chat │ │Teach 3│ │ Auto │
└──────┘ └──────┘ └──────┘      └──────┘ │ (RED) │ └──────┘
                                          └───────┘
```

- **Click Teach (not recording)** → `toggleTeachRecording(webappId)` flips the per-webappId flag in the drawer store. Existing 09-06 useEffect in `webapp-stream-window.tsx` observes the flip and calls `recorder.start({webappId, vncRef})`. Button background flips to `bg-red-500/90`.
- **Live click counter** — as the recorder captures events (clicks, keys, wheel, scroll, heartbeat waits), it pushes to its internal `events` state. The stream-window mirrors that array to the drawer store via `setTeachEvents(webappId, recorder.events)` in a useEffect. The IconBar reads `events = s.teachEventsByWebappId[webappId] ?? EMPTY_TEACH_EVENTS`; `clickCount = events.length`. Badge JSX (`absolute -top-1 -right-1 min-w-[18px] h-[18px] rounded-full bg-red-600 text-white text-[10px] font-semibold ... ring-2 ring-white`) renders the count only when `isRecording && clickCount > 0`.
- **Click red Teach button (recording)** → same `toggleTeachRecording(webappId)` wire. Existing 09-06 useEffect observes the flip back to false → `recorder.stop()` → if events captured, `SaveSkillDialog` opens (unchanged). Empty recordings → silent server-side discard via `skills.discard.mutate({sessionId})`.
- **No top-right widget anywhere** — the `TeachRecordingOverlay` JSX render is removed from `webapp-stream-window.tsx`; the function definition + props interface are deleted; the `Square` lucide-react import is dropped.
- **No time elapsed display** — `webapp-teach-popup-host.tsx` already contained no `Date.now()` / `elapsed` / `seconds` references. T-09-09-05 locks that absence forward-looking.
- **Aria-label dynamic** — `aria-label="Stop teaching (3 clicks)"` while recording, `aria-label="Teach"` otherwise. Screen readers get the live count too. Tooltip content mirrors.

## Deviations from Plan

Three minor deltas — all under Rule 1/3 auto-fix scope; none affecting the user-facing contract:

1. **[Rule 3 - Blocking issue] Hook signature unchanged.** The plan's `<interfaces>` block sketched `const recorder = useTeachRecorder(webappId); const clickCount = recorder.events.length` inside the IconBar. But the existing hook signature is `useTeachRecorder(): UseTeachRecorderResult` (no arg) and the recorder is local-per-call state (96-CONTEXT §gray-area #7). Calling it from the IconBar (a sibling component to webapp-stream-window) would yield an independent fresh recorder, not the active one. Adopted the parent-mirrors-to-store pattern instead: the recorder's existing `events: readonly ActionEvent[]` exposure (added in 09-06) is mirrored into a new drawer-store slot `teachEventsByWebappId` via a useEffect in `webapp-stream-window.tsx`; the IconBar reads from the store. Same data, no hook signature change, no risk to existing 96-04/96-05/96-06 callers. The plan's literal `events.length` regex assertion (T-09-09-02) is still satisfied — the IconBar's local `events` const is read from the store and `.length` is called on it directly. The hook's `events` field continues to exist and is the source of truth.

2. **[Rule 1 - Bug] EMPTY_TEACH_EVENTS frozen sentinel.** Without a stable empty-array reference, the IconBar's Zustand selector `s.teachEventsByWebappId[webappId] ?? []` would return a fresh `[]` on every render where the WebApp hasn't started a recording yet — breaking Zustand's `shallow-equality`-based memoization and causing infinite re-render loops. The fix: export a `Object.freeze([])` sentinel from the store module; consumers fall back to that. Same precedent as `useReducer`'s recommended pattern for default state. This was discovered during the implementation pass; not in the plan, but a Rule 1 correctness requirement.

3. **[Rule 1 - Bug] Regex shape on T-09-09-01 forced specific source token order.** The plan's `<interfaces>` sketch wrote `className={cn('relative', isRecording && 'bg-red-500/90 text-white hover:bg-red-500')}`. The IconBar's structure renders all three icons in a `.map()`, so the conditional needs the Teach-icon guard. First attempt used `isRecording && id === 'teach' && 'bg-red-500/90 ...'` which placed `id === 'teach'` between `isRecording` and the literal string, failing the regex `/isRecording\s*&&\s*['"`][^'"`]*bg-red-500/`. Reordered the guard tokens to `id === 'teach' && isRecording && 'bg-red-500/90 ...'` so the regex matches (the substring `isRecording && 'bg-red-500/90 ...'` IS present in this order). Behaviorally identical to either ordering; the source-text invariant locks a specific token order to make the contract grep-friendly for future readers.
