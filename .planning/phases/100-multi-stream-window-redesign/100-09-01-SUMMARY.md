# Phase 100-09-01: Window-Scoped Screenshot Hex Wid Argv Summary

**One-liner:** Switch `maim -i <wid>` argv from decimal to canonical `0x<hex>` form so bytebot's `computer_screenshot` tool returns the bound WebApp window framebuffer (1280x720) instead of silently degrading to full Xvfb root capture (1920x1080).

**Date completed:** 2026-05-09
**Sacred SHA gate:** PASSED (byte-identical pre + post all commits).

## Goal

Bytebot `computer_screenshot` tool returns the WebApp's bound window only (1280x720 per 100-08-02 `--window-size=1280,720`), NOT full Xvfb :1 (1920x1080). Closes Bug 1 from 100-08 deploy live test (UAT row "screenshot returns Gmail window only, not full Xvfb").

## Root cause

`screenshot.ts:115` was building maim argv as:

```ts
['-i', String(windowId), tempPath]   // DECIMAL — silently degraded on Ubuntu 24.04 maim 5.7.4
```

The codebase-canonical X11 wid form everywhere else (`streaming/vnc-bridge.ts:61`, xdotool argv throughout `input.ts`, all `_NET_WM_*` reads) is `0x<hex>`. Empirically on Ubuntu 24.04's `maim 5.7.4`, decimal-form ids fall through to root capture (or scrot fallback, also full-display). Hex form parses unambiguously.

The env wiring path (`buildBytebotConfig` → `BYTEBOT_TARGET_WINDOW_ID=<decimal>` env → `mcp/server.ts:42` parseInt → `defaultWindowId` → `tools.ts:266` wid resolver → `captureScreenshot({windowId: w})`) was already correct from 100-08-04. The bug was ONLY the in-`screenshot.ts` decimal-vs-hex argv encoding.
