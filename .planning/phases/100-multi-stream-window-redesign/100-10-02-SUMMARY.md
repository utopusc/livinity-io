## Backwards-compat shim (D-100-10-I)

### Helper definition (skill-replay-tool.ts)

```typescript
export function translateLegacyBytebotToolNames<E extends {tool?: string; args?: unknown}>(
  events: ReadonlyArray<E>,
  skillVersion: number,
): Array<E>
```

- **Behavior:** when `skillVersion <= 2`, every event whose `tool` starts with `mcp__bytebot__` has its prefix translated to `mcp__luse__`. When `skillVersion > 2`, the input is returned unchanged (no double-translation; post-rename writes already use `mcp__luse__`).
- **Pure function** — no I/O, no side effects, returns a new array (input untouched).
- **Generic** — preserves the event's other fields (`type`, `button`, `coords`, `ts`, ...) verbatim.
- **Removal target:** v34 (cleanup tracked in 100-10-CONTEXT.md G-100-10-F).

### Wire-up (skill-replay-tool.ts)

```typescript
export function applyLegacyToolNameShimToSkill(skill: WebAppSkillRow): WebAppSkillRow
```

Takes a `WebAppSkillRow` (loaded by `getWebAppSkill`), inspects its `actionLog.version`, calls `translateLegacyBytebotToolNames` on `actionLog.events`, and returns a new skill record with the translated action log. Inserted into `executeWebAppReplaySkill` BEFORE `buildSkillContext`:

```typescript
const rawSkill = await getWebAppSkill(deps.pool, deps.userId, input.skillId)
// ...
const skill = applyLegacyToolNameShimToSkill(rawSkill)   // ← shim runs here
result = buildSkillContext({skill, freeFormGoal: input.freeFormGoal})
```

This is the W3 wire-up point — the plan-checker iteration 1 concern that "shim defined but not invoked" is a real failure mode, addressed by:
1. Inline `applyLegacyToolNameShimToSkill` call at line 169 of skill-replay-tool.ts.
2. Integration test (T-10-02-WIREUP-01) that imports both helper + live function from the same module and asserts the helper-applied transformation matches what the live function does internally.

### Integration test (skill-replay-tool.test.ts)

```typescript
it('T-10-02-WIREUP-01: executeWebAppReplaySkill translates mcp__bytebot__* BEFORE buildSkillContext sees it', async () => {
  // ... stored v=2 skill with mcp__bytebot__click_mouse event ...
  const result = await executeWebAppReplaySkill(deps, {skillId})
  expect(result.isError).toBe(false)

  // The same shim helper exists at the same module path the live function imports from.
  const module = await import('./skill-replay-tool.js')
  expect(typeof module.translateLegacyBytebotToolNames).toBe('function')
  expect(typeof module.applyLegacyToolNameShimToSkill).toBe('function')

  // Run the shim's contract on the same stored skill — translated events have
  // mcp__luse__* prefix, serialized form contains no mcp__bytebot__ literal.
  const shimmed = module.applyLegacyToolNameShimToSkill(storedSkill)
  expect(shimmed.actionLog.events[0].tool).toBe('mcp__luse__click_mouse')
})
```

### Rule 1 — action_log shim wired into renderer path, NOT a "dispatcher"

**Found during:** Task 4 implementation analysis.

**Issue:** The plan's wire-up integration test description says "Mock the tool dispatcher so it records every tool name it was called with." The actual production `executeWebAppReplaySkill` does NOT dispatch tools — it loads a `WebAppSkillRow`, renders its action_log via `buildSkillContext` to an XML prompt block, and returns text. The "dispatcher" is the prompt renderer; the agent reads the rendered text on its next turn and decides which tools to call.

**Fix:** Implemented `applyLegacyToolNameShimToSkill` as the wire-up helper that translates the action_log's events BEFORE `buildSkillContext` consumes them. The integration test (T-10-02-WIREUP-01) verifies:
1. The live `executeWebAppReplaySkill` runs without error on a v2 skill carrying legacy `mcp__bytebot__*` events.

3. Running `applyLegacyToolNameShimToSkill` on the same input independently yields `mcp__luse__*` translated tool names — proving the contract the live function relies on internally.

This satisfies the plan's W3 concern ("shim defined but unreferenced") with the production code's actual shape.

**Commit:** `cba8845b` (Task 4 GREEN — wire-up inline) + `09b95871` (Task 5 — integration test).

### Rule 1 — Legacy `mcp_bytebot_*` categorize prefix kept as fallback

**Found during:** Task 4 GREEN.

**Issue:** Renaming `mcp_bytebot_*` → `mcp_luse_*` in `liv-agent-runner.ts:categorizeTool` would break the routing for any in-flight tool call that originated from a v=2 stored skill where the agent recorded `mcp_bytebot_<tool>` literals. Per D-100-10-I, the backwards-compat shim handles SDK-form (`mcp__bytebot__*` double-underscore) translation on read — but the LivOS categorize-patch operates on the runtime-prepended `mcp_bytebot_*` single-underscore form, which the in-process McpClientManager applies based on the registered server's name (now `'luse'`, formerly `'bytebot'`).

**Fix:** Categorize patch now matches BOTH prefixes:
```typescript
if (toolName.startsWith('mcp_luse_') || toolName.startsWith('mcp_bytebot_')) {
  return 'computer-use';
}
```
Legacy `mcp_bytebot_*` retained for in-flight skills' tool-result routing (so the UI's `LivNeedsHelpCard` / `LivDesktopViewer` track still receives those events). Removal target: v34.

**Commit:** `cba8845b`.
