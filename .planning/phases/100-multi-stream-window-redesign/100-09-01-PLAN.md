**Root cause analysis (live data + code read):**
- Per-WebApp MCP children spawned by 100-08-04 carry `BYTEBOT_TARGET_WINDOW_ID=<wid>` env. `mcp/server.ts:42` parses it into `defaultWindowId`. `tools.ts:266` (`computer_screenshot` handler) calls `captureScreenshot({windowId: w})`.
- `screenshot.ts:115` builds maim argv as `['-i', String(windowId), tempPath]` — **decimal** form.
- `maim -i <id>` documentation: id is parsed as a decimal X11 window id by recent maim builds, BUT older / packaged maim (Ubuntu 24.04 `maim 5.7.4`) treats numeric ids as opaque X11 cookies; the canonical X11 form everywhere else in this codebase is `0x<hex>` (`vnc-bridge.ts:61`, xdotool wid args, `_NET_WM_PID` reads).
- The decimal-vs-hex inconsistency is the empirical failure mode: `maim -i <decimal>` either silently captures the root window OR errors back into the scrot fallback path (which is host-display always; `screenshot.ts:158-163`).

**Fix:** Match the codebase-canonical `0x<hex>` form. Same shape as `vnc-bridge.ts:61` `widHex = '0x' + opts.wid.toString(16)`.

// buildBytebotConfig with a PerWebAppMcpDescriptor) sets BYTEBOT_TARGET_WINDOW_ID

if (targetWindowEnv) {

    }
