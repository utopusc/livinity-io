# Phase 272 Plan 01 — cli-auth-dialog paste-back UX (AUTH-1/2/3)

<objective>
Make the LivOS cli-auth dialog's paste-back flow actually usable: surface the paste field immediately (AUTH-1), make the API-key fallback first-class (AUTH-2), and make the code field visible + Enter-submittable (AUTH-3). Then re-promote the fixed dialog as the default `cli-auth` path (Terminal kept as the in-dialog "Advanced" fallback), since the dialog's only blocker (AUTH-1 infinite spinner) is now fixed. Single-file UI change + a one-line bridge re-wire.
</objective>

<must_haves>
- AUTH-1: in the `auth-paste-back` branch the code-paste field renders IMMEDIATELY (not gated on `deviceCode`); the "Open link" block stays conditional on `deviceCode`. No path leaves the user on a spinner-only "Waiting…" with no way to paste.
- AUTH-2: "Use an API key instead" is a real `<Button>` (secondary/default variant), not a `text-caption` gray link, shown when `method?.apiKeyEnv` exists.
- AUTH-3: the paste-back code field is a VISIBLE input (not `<PasswordInput>`), `autoFocus`, and Enter submits it (`handleSubmitPasteCode`). The API-key field also submits on Enter (`handleSubmitApiKey`). The pasted code is still cleared on submit and never logged/persisted (E-9 contract intact).
- Routing: `use-cli-auth-bridge.ts` `cli-auth` opens the dialog (`openCliAuthDialog({cli, mode:'auth'})`); `cli-install`/`cli-uninstall` unchanged; NAME-only RCE boundary preserved.
- `pnpm --filter ui` typecheck introduces ZERO new errors vs baseline (repo tsc is broken at baseline; verify via stash-diff or per-file).
</must_haves>
