## Deviations from Plan

### Rule 3 — Mini PC catalog HSET ratchet (deployment-side, NOT in repo)

**Found during:** Task 3 (Mini PC re-seed prep).

**Issue:** `update.sh` runs `_dld_seed_mcp_servers` (the Phase 109 install helper) but that helper is D-109-IDEMPOTENT — when `liv:mcp:config` already exists as a HASH (the post-Phase 219 steady state), it SKIPs the substitution + HSET. So upgrading an existing v43-shipped box via `update.sh` writes the new payload to the FS but never lands it in Redis. The seed orchestrator (`seedAionUiMcpConfig`) then reads stale Redis entries (old 3-key luse env, old `enabled: false` on 4 local MCPs), and Phase 241's strict GET-and-skip means the existing AionUi entries are preserved as-is even after the re-seed runs.

**Fix:** one-shot ratchet executed via SSH on Mini PC:
1. Fetch fresh seed JSON from GitHub master (raw URL).
2. Substitute 4 placeholders against host-local `REDIS_URL` + `LIV_API_KEY` + slug `bruce` + domain `livinity.io`.
3. `HSET liv:mcp:config <name> <substituted-json>` for each of the 5 system MCPs (per-field HSET preserves operator's `filesystem` entry).
4. DELETE all 5 system MCPs from AionUi via `DELETE /api/mcp/servers/{id}` (HTTP 200 × 5).
5. `redis-cli DEL livos:v43:mcp_seeded:v1`.
6. `sudo systemctl restart livos`.
7. Phase 241 boot orchestrator re-seeds AionUi from the new catalog state.

**Files modified:** None in repo (deployment-side fix only).
**Commit:** N/A (deployment-side; documented here per Rule 3 protocol).
**Mirror precedent:** Phase 241-04 Rule 3 deviation — same pattern (catalog HSET pre-deploy) for the same root cause (D-109-IDEMPOTENT skips on existing HASH). Phase 245.1 expands the procedure with a DELETE+sentinel-DEL step to force AionUi-side re-seed.

**Follow-up consideration:** Three forward options for future phases to remove the manual ratchet:
- (a) Add a separate `_dld_upgrade_mcp_seed` helper to `update.sh` that diffs the seed JSON against Redis and conditionally HSETs changed system entries (keyed by D-241-01 SYSTEM_MCP_NAMES so operator-added entries stay untouched). Risky — every update.sh would overwrite operator UI edits to system MCPs.
- (b) Bump the sentinel version key (e.g., `livos:v43:mcp_seeded:v2`) so the next boot's Stage 0 short-circuit doesn't fire and the orchestrator forces a re-read. Still doesn't fix the stale Redis catalog problem — only useful if combined with (a).
- (c) Move the catalog source-of-truth out of Redis and into a versioned static JSON file on disk, with Redis only holding operator-overlay diffs. Cleaner long-term but a v44+ refactor.

Decision deferred. Phase 245.1's 3-commit ratchet is correct and complete for the immediate v43 hotfix; the upgrade-path question is a separate v44 design topic.
