`vault.items.create` mutation input (Zod schema from vault-items-router.ts lines 60-70):
```typescript
const createInput = z
  .object({
    type: z.enum(['project', 'agent', 'chat']),
    name: z.string().min(1).max(200),
    parentId: z.string().regex(/^[0-9A-Za-z_-]{20,}$/).nullable().optional(),
    cwd: z.string().optional(),       // project-only — server runtime-gates
    schedule: z.string().optional(),  // agent-only  — server runtime-gates
    ccSessionId: z.string().optional(),// chat-only — server runtime-gates
  })
  .strict()
```

CROSS-TYPE FIELD GATING (vault-items-router.ts lines 155-169) — the server runtime-rejects with BAD_REQUEST if:
- `type !== 'project'` AND `cwd !== undefined`
- `type !== 'agent'` AND `schedule !== undefined`
- `type !== 'chat'` AND `ccSessionId !== undefined`

⇒ The CLIENT MUST NOT send `cwd` on agent/chat creates, MUST NOT send `schedule` on project/chat creates, MUST NOT send `ccSessionId` on project/agent creates. Per-type form state MUST be isolated — when the user switches type, prior-type-only fields are NOT carried over.

`vault.items.create` returns `{item: Item}` on success.

Server-authoritative fields the client MUST NOT include in the mutation payload:
- `id`, `createdAt`, `updatedAt`, `archivedAt`, `schemaVersion`, `userId`
The server generates these. Passing them via `.strict()` Zod will reject the whole request.

`parentId` handling:
- The 175-01 parent dropdown uses MAIN_LIV_ID ('main-liv') for the synthetic root. THIS literal MUST be translated to `null` when sending to the server (the server's `parentId` regex `/^[0-9A-Za-z_-]{20,}$/` requires ≥20 chars; 'main-liv' is 8 chars and would Zod-reject).
- Rule: `serverParentId = parentId === MAIN_LIV_ID ? null : parentId`

## Trust Boundaries

- **Trust boundary 1 (form input → tRPC):** User-entered name/cwd/schedule/systemPrompt strings flow into the mutation payload. The server's Zod `.strict()` schema rejects unknown fields; `name` is length-bounded (min 1, max 200); `parentId` is regex-validated. The client adds defence-in-depth via `String.trim()` and length checks but the server is the gate.
- **Trust boundary 2 (mutation onError.message → toast):** The server's error message string is rendered as React text via `toast.error(err.message)`. React's default JSX escaping prevents HTML/XSS injection in the toast surface. sonner itself uses text nodes (no `dangerouslySetInnerHTML`).
- **Trust boundary 3 (parentId dropdown selection → mutation):** The dropdown value is constrained to MAIN_LIV_ID OR Item.id values returned by `vault.items.list` (server-trusted). Translation `MAIN_LIV_ID → null` is the only client-side transform; otherwise the value is sent verbatim and the server's regex validates.
